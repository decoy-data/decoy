## How `win-run` works

Usage: `win-run <cli|engine> <worktree> '<cmd.exe command>'`. In the command, `%PY%` is the venv
python, `%VENV%` the venv root, `%SHA%` the head. Example:
`win-run cli ~/vscode/wt-x '%PY% -m pytest tests\unit\library -q'`.

1. The worktree must have no uncommitted tracked changes. The lane tests an exact head.
2. The devbox takes `~/.cache/winrun.lock` (jobs queue), then ssh checks `dell-win` works.
3. It copies `winrun.ps1` and `winrun_plugin.py` to the Dell (copy, then `move /Y`, so a running job
   never sees a half file) and sends a git bundle of HEAD. The bundle is incremental when the Dell
   already has the merge base with `origin/main`, otherwise the full history.
4. On the Dell the runner takes `C:\dc\win-run.lock`, reads the token type, Windows build, OpenSSH
   version, free and total memory and the `.wslconfig` cap, and writes them to the log.
5. Memory gate: below `WINRUN_MIN_FREE_GB` (default 6) of free memory it waits `MemWaitMin` (10)
   minutes, then refuses and exits 75. Memory comes from `GlobalMemoryStatusEx`, because WMI is
   denied to the standard user over ssh.
6. It fetches the bundle, checks out the SHA detached, runs `git clean -fdx`, and requires
   `git rev-parse HEAD` equal to the SHA and an empty `git status --porcelain`. The log line is
   `win-run: SHA requested <sha> observed <sha> tree clean`.
7. Venv: the SHA-256 of `requirements-dev.lock` (cli) or `uv.lock` (engine) names the venv path, so a
   changed lock builds a new venv. CLI: `uv pip sync` of the lock, then `colorama` (the lock was
   compiled on Linux and pytest needs colorama on Windows), then `uv pip install --no-deps -e .` on
   every run. Engine: `uv sync --frozen --extra dev --extra lint --extra vault --extra cloud`, the
   same extras as the engine's `bootstrap.sh`. Python is always the uv-managed 3.10.20.
8. The job runs through a generated `.cmd` file. Output streams to the devbox and into
   `~/.cache/win-run/logs/<label>.log`. The last line is `EXIT n`.
9. Stall guard: no output for `WINRUN_STALL_MIN` (default 15) minutes, or `WINRUN_TIMEOUT_MIN`
   (default 90) in total, kills the job's own process tree by PID, prints `WINRUN STALLED ...`
   and exits 124. Same convention as `vm-run`. Tested with `WINRUN_STALL_MIN=1` and a silent
   `ping`: exit 124 after one minute, no `ping.exe` left. `taskkill /T` printed one
   "Access denied" line for a protected child, and the tree still ended.
10. AT-LANE-1: `winrun_plugin.py` is loaded through `PYTEST_ADDOPTS`. A skipped test marked
    `windows` fails the run (exit 1 and a `WINRUN FAIL` line). The devbox wrapper also counts a log
    without the SHA line or the final `EXIT` line as failed.
11. Last step: it appends `DONE win-run <label> rc=N <HH:MM>` to the codex queue log at
    `/tmp/claude-1000/-home-cam/9872cccf-1826-4b8b-811b-b842b8672e42/scratchpad/cq/queue.log`.

Only PIDs started by the run are killed. The runner never touches WSL, the engine CI runners or
`.wslconfig`. There is no Defender exclusion. Standard runs never call the admin identity. The
`.wslconfig` cap is read once with `win-run --refresh-wslconfig-cap` (a read-only `type` through
`dell-win-admin`, because `decoyci` cannot read the admin user's profile) and cached in
`~/.cache/win-run/wslconfig-cap` with the date. Each run logs the cached value and its age, for
example `wslconfig cap 44GB_cached_2026-11-18_age_0d`. With no cache it logs `unknown_no_cache`
and the run goes on. Refresh the cache when `.wslconfig` changes.

Other guards: `git clean` failing, a failed `uv venv`, the colorama install or the editable install
fails the run before `.ok` is written. `WIN_RUN_WHEEL` is refused unless `WIN_RUN_WHEEL_SHA256` is a
full 64-character hex string, and the runner re-checks that before it compares hashes.

Not built in this slice (still in the WR row): the nightly cron entries, the node-watch entry, a
timing-retry record (a retry is a second `win-run` call and both logs stay), and the dated vault
runbook.

## Native companion wheel

- `engine-win`: built on the Windows host from the exact engine SHA with `maturin`, as
  `native-companion-release.yml` does for `windows-latest` (`--release --locked --compatibility
  pypi`, target `x86_64-pc-windows-msvc`). The job records the wheel hash before it installs the
  wheel. This needs Rust and the MSVC Build Tools on the Dell. They are not installed. The Build
  Tools install and licence step is left to the first slice that needs it (owner decision if it asks
  for a licence prompt).
- `demo-win`: receives the exact E-REL Windows companion wheel (the asset the candidate's engine pin
  selects, from the engine GitHub release) and its checksum from `SHA256SUMS`. The devbox downloads
  it, then calls `WIN_RUN_WHEEL=<file> WIN_RUN_WHEEL_SHA256=<hex> win-run ...`. The runner copies
  the wheel to `C:\dc\wheels`, compares the hash and stops on a mismatch. The job installs it
  separately with `uv pip install --no-deps "%WIN_RUN_WHEEL%"`.
- No companion wheel is installed in the venvs today. The proof run below did not need one.

## Windows update and reboot pause

Set in the registry through `dell-win-admin` without a reboot:

- `HKLM\SOFTWARE\Microsoft\WindowsUpdate\UX\Settings`: `PauseUpdatesExpiryTime`,
  `PauseFeatureUpdatesEndTime` and `PauseQualityUpdatesEndTime` are `2026-12-05T00:00:00Z`. The
  start values are 2026-11-18T22:14:11Z.
- `HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate\AU`: `NoAutoRebootWithLoggedOnUsers=1`,
  `NoAutoUpdate=0`, `AUOptions=2` (notify before download, so nothing installs and restarts on
  its own).

No reboot was pending when this was set. Windows may still cap or ignore a pause on a preview
build, so the check at each lane run is the build number in the log header. Remove these values
after the 2026-12-04 D-4 cut if routine updates should resume.

## Facts found during setup (for R0)

- `uv python install` fails on this build when it makes its minor-version link: "The path cannot be
  traversed because it contains an untrusted mount point (os error 448)". The interpreter itself is
  installed and works. The runner removes nothing and uses `uv python find 3.10.20`; the
  `cpython-3.10-...` junction was deleted by hand.
- WMI and CIM are denied to the standard user over ssh (`Get-CimInstance` returns Access denied).
- `decoyci` cannot read the admin user's `.wslconfig`.
- `taskkill /T` on the job tree reports one Access denied line for a child and still ends the job.
- The CLI lock installs and `decoy --version` runs on Windows (`decoy 0.1.0`).
- The engine does not import on Windows at this head: `os.O_DIRECTORY` is missing in
  `decoy_engine/fileaccess/_output.py`. This is the gap EW1 closes. Every CLI test that imports
  `decoy_engine` fails at collection until then.

## Negative cases (real runs, 2026-11-18)

Run from a scratch commit on top of `origin/main` (`f1da00f5`) that adds one test marked `windows`
and skipped. The scratch branch is not pushed.

| Case | Command | Result | Log |
|---|---|---|---|
| Skipped `windows` test | `%PY% -m pytest tests\sentry\test_winrun_neg.py -q` | `WINRUN FAIL: windows-marked test skipped: ...`, `EXIT 1`, rc 1 | `~/.cache/win-run/logs/w435ee7-3948575-1795040437.log` |
| No final `EXIT` line | `WINRUN_TEST_DROP='^EXIT' win-run cli . 'echo ok'` | "log lacks the SHA line or the final EXIT line", rc 255 | `~/.cache/win-run/logs/w435ee7-3949392-1795040447.log` |
| No SHA line | `WINRUN_TEST_DROP='^win-run: SHA requested' win-run cli . 'echo ok'` | same message, rc 255 | `~/.cache/win-run/logs/w435ee7-3950339-1795040456.log` |
| Low memory | `WINRUN_MIN_FREE_GB=500 win-run cli . 'echo ok'` | waits 10 min, "refused, free memory 21.9 GB is below 500 GB", `EXIT 75`, rc 75 | `~/.cache/win-run/logs/w435ee7-3951260-1795040467.log` |
| Wheel without a hash | `WIN_RUN_WHEEL=/tmp/x.whl win-run cli . 'echo ok'` | refused before any copy, rc 255 | none (devbox refusal) |

The two missing-line runs used a test-only `WINRUN_TEST_DROP` filter that deleted matching lines
before the log was written. Review showed it could also delete the `WINRUN FAIL` line and turn a
failing run into a pass, so it was removed from `win-run` after these runs. The refusal case also prints the missing-line message, because the memory gate
runs before the SHA proof. The refusal keeps its own exit code 75.

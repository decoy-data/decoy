## 0. Summary for the owner

The bar (owner 2026-11-18): a user downloads the signed CLI bundle from the download page, installs
it on Windows, and `decoy demo` plus the basic quickstart run work end to end.

What stands between main and that bar, from the static census in section 1.3 (R0 confirms it on a
real Windows machine):

1. **The engine does not import on Windows.** Four module-scope POSIX names fail at import time.
2. **Every engine run that writes output fails on Windows.** F22 publication raises
   `LockUnavailable(ENOSYS)` on win32 (`E:fileaccess/_local.py:536`). The demo writes output, so the
   F22 Windows arm (engine slice w1; the build state lists it as Later under row 59) is on the
   critical path. This plan moves it into 1.0 (Q10).
3. **The installer and the runtime layout are POSIX-shaped.** `current` is a symlink, the launcher is
   a shell script, the install lock is `flock`, and `install.ps1` needs `openssl`, which a stock
   Windows machine does not have. Windows is gated off by one lever (`C:distribution/targets.py:28`).
4. **Private files on Windows inherit their folder's ACL.** The CLI's one mode module says so
   (`C:_private_file.py:97-104`). A vault written under a folder that grants Authenticated Users
   read access is readable by other local users.
5. **No release leg builds a Windows bundle**, and no CI lane runs anything on Windows.

The plan: one feasibility record first (R0), then 12 build slices (4 engine, 7 CLI, 1 infra, plus an
engine release on the existing train), each under 800 lines, each fixing one concern at one choke
point. Total about 3,900 lines including tests.

Timing risk, stated plainly: the owner said building happens after the main 1.0 build (from about
2026-12-04) and must finish before CLI-REL, aiming for about 2026-12-15. The engine freeze (REL-GATE
G1, the D-4 tag) is the last daily engine release after 2026-12-04, so engine slices built after it
need a patch release that reopens G1 to G3. Q1 asks to build the four engine slices before the D-4
tag (they add win32 arms only and leave POSIX code unchanged). Q7 asks for a cut line if the
Windows slices are not green in time.

## 1. FRAME

### 1.1 Problem

Windows is in 1.0 (owner 2026-11-18, CLI `docs/roadmap/decisions.md:13-15`). The packaging spec has
always listed a Windows target, the engine's native companion builds a Windows wheel in CI, and
`install.ps1` exists, but no part of the lifecycle has run on Windows because no runner existed
(`docs/distribution/decisions/2026-10-26-windows-target-gated.md`, "Context"). The LIB evidence
records say the same: Windows-only cases are written and skip-marked, "Windows: NOT RUN (no
runner)" (`docs/records/lib-l1b3-evidence.md:110`).

### 1.2 Guarantee (what 1.0 promises on Windows)

On Windows 11 x64 (and the Windows Server 2022 CI image), with Windows PowerShell 5.1 and no extra
tools installed:

- G1 Install. The PowerShell one-liner on the download page installs the signed bundle. The
  installer verifies the version document and the bundle signature before anything is extracted,
  with no `openssl` on the machine. A failed or impossible verification is a refusal with nothing
  installed.
- G2 Demo and quickstart. `decoy --version`, `decoy doctor`, `decoy demo` and the quickstart
  (`decoy init` then `decoy run` on the demo config) exit 0 and write the same output bytes as on
  Linux for the same input, key and config (Q6).
- G3 Upgrade and rollback. `decoy upgrade` from a running 1.0.x to a newer version, and rollback,
  work while the old version is running, and never leave a half-deleted version directory live.
- G4 Private files. Every file and directory the CLI or engine creates as private (vault, staging,
  scratch, the install lock) is created with a protected DACL that grants the current user and
  SYSTEM only, from its first instant, or the operation refuses.
- G5 Locks. The install lock, the vault lock and the publication lock exclude a second process on
  Windows as they do on POSIX.
- G6 Typed refusals. Every engine and CLI feature that is not Windows-capable in 1.0 refuses with a
  registered code before any write, never with `AttributeError`, `ImportError` or a half-written
  output. The list is section 5 (Later) and goes into the install docs.

Non-goals (1.0): Windows ARM64 (refused at target detection, Q2); the strict file-access policy
(CPython has no `dir_fd` on Windows); the isolated route (it sets `resource` limits); directory
fsync durability on Windows (F22 named limit L1w); an `.exe` launcher; MSI, winget or scoop
packages; network shares and cloud-synced folders as output roots beyond the existing reparse-point
refusal; the full test suites on Windows (only the lane set in section 4.3 runs there).

### 1.4 Failure modes this plan designs against

- F1 A Windows install that looks verified but is not (a missing verifier silently skipped).
- F2 An upgrade that deletes part of the running version and then rolls back onto it.
- F3 A private file that exists for a moment with an inherited, broader ACL.
- F4 Two upgrades or two publishers at once because the Windows lock arm is a no-op.
- F5 A path over 260 characters inside the bundle that fails extraction on a stock machine.
- F6 A POSIX regression from a new win32 arm.
- F7 A scattered `if os.name == "nt"` that a later change misses.
- F8 Output bytes that differ by OS (line endings, encoding), which would break the determinism
  promise across machines.
- F9 A release that advertises Windows while a lane is red (the 2026-10-26 failure).

## 2. Established solutions (survey)

Searches run for this plan: web searches on Windows atomic replace semantics, Artifact Signing
pricing and eligibility, the OpenSSH client shipped with Windows, and how uv's PowerShell installer
works; codebase searches in both repos for `os.name`, `sys.platform`, `fcntl`, `msvcrt`, `ctypes`,
SDDL, `os.replace`, `symlink`, `killpg` and `resource`.

- **Atomic replace on Windows.** `os.replace` is `MoveFileExW(MOVEFILE_REPLACE_EXISTING)`. It is
  atomic for a file on one NTFS volume but fails with a sharing violation or access denied while
  another process holds the target open without `FILE_SHARE_DELETE` (CPython opens files without
  it). `ReplaceFileW` has the same constraint and adds backup semantics Decoy does not need.
  Established handling: Git for Windows `mingw_rename` retries the move for a short bounded time,
  then fails. The CLI already does this in one place, `C:_atomic.py:532` `_retry_on_windows`
  (10 attempts, 950 ms), and F22 5.8 uses the same bounded retry. A directory cannot be replaced by
  `MoveFileExW`; an exclusive `os.rename` onto an absent name is the bind (F22 5.8).
- **Running executables.** Windows refuses to delete or rename a directory that holds a running
  image or a loaded DLL. rustup self-update renames its running exe aside and deletes it on a later
  run; uv's `self update` uses the `self-replace` crate, which does the same. Decoy never replaces a
  running file: each version lives in its own directory and only a pointer changes, as on POSIX.
  Pruning an in-use version is deferred to a later run (CW3).
- **Pointer without symlinks.** A symlink needs Developer Mode or admin. A directory junction needs
  no privilege but cannot be replaced atomically (it is a directory). A small pointer file replaced
  with `os.replace` is atomic and needs no privilege; it is the first option the 2026-10-26
  decision lists ("a `current.txt` pointer read by a `.cmd` launcher").
- **Owner-only ACLs.** The established pattern is a protected DACL set at creation through
  `SECURITY_ATTRIBUTES` (`CreateFileW`, `CreateDirectoryW`), never a mode change after the fact.
  The engine already has it: `E:fileaccess/_protected_dir.py:366` (SDDL
  `D:P(A;OICI;FA;;;<user SID>)(A;OICI;FA;;;SY)`), `:374` `_win_create`, `:384` `_win_create_file`,
  `:407` `_win_tighten`, written for LIB L0.1 from the same survey (pywin32 and `icacls` were
  rejected there to avoid a new dependency and a subprocess). This plan reuses that code and adds
  no second ACL implementation.
- **Locks.** `filelock`'s `WindowsFileLock` and `portalocker` use `msvcrt.locking(fd, LK_NBLCK, 1)`
  on byte 0 of a dedicated lock file; the OS releases it when the handle closes or the process dies.
  F22 5.8 already chose this for the publication lock. Shared locks need `LockFileEx` (portalocker's
  Windows arm); EW2 decides from R0 whether the engine's one shared lock
  (`E:fileaccess/_scratch.py:174`) needs to be shared on Windows.
- **Installer and verification.** uv and rustup ship a PowerShell installer run as
  `powershell -ExecutionPolicy ByPass -c "irm <url> | iex"`, unpack into the user profile and add a
  user-scope PATH entry (HKCU). Windows 10 1803 and later ship `tar.exe` (bsdtar), so the existing
  `.tar.gz` bundle needs no second archive format. Windows PowerShell 5.1 has no Ed25519, so the
  verifier follows MAC-ED25519: an OpenSSL route if a good `openssl` is present, else SSHSIG through
  the built-in OpenSSH client's `ssh-keygen -Y verify` (OpenSSH for Windows is installed by default
  on Windows 10 1809 and later and on Windows 11, per Microsoft's OpenSSH overview; `-Y` exists
  from OpenSSH 8.1). The OpenSSH version shipped differs by Windows build, so R0 records the actual
  version and the known-answer result on Windows 11 and Server 2022. No custom crypto in PowerShell.
- **Code signing.** Authenticode is the Windows trust mark. Microsoft Artifact Signing (renamed
  from Trusted Signing) is USD 9.99 a month for the Basic tier with 5,000 signatures; Microsoft
  opened it to individual developers in 2024, and current notes say individuals in the US and
  Canada can validate (azure.microsoft.com pricing page and Microsoft's preview announcement,
  checked 2026-11-18; to be confirmed at sign-up). `jsign` signs PE files and PowerShell scripts with
  it from Linux, so it fits the existing Linux `sign` job of `release.yml`. Authenticode is not on
  the bar's path: a file fetched by `Invoke-WebRequest` and unpacked by `tar.exe` carries no
  Mark-of-the-Web, so SmartScreen does not prompt, and the Ed25519 and SSHSIG signatures stay the
  integrity check on every platform. It helps users who run `-ExecutionPolicy AllSigned` (Q3).
- **Long paths.** `MAX_PATH` is 260 unless `LongPathsEnabled` is set and the program is manifested
  for it. pip and uv keep install roots short; Decoy checks a path budget at build time instead
  (CW4), as the CLI already does for the library root (`C:cli/library/_paths.py:74`).
- **Process kill.** `os.kill(pid, signal.SIGTERM)` on Windows calls `TerminateProcess`;
  `subprocess.Popen.kill()` is the portable form. A process-tree kill needs Job Objects (Later).

Custom code left: the pointer file and its readers, the build-time path budget, the PowerShell
verifier selection (a port of MAC-V1a's shell logic), the lock arm (a few lines), and the slot prune
rule. Each is small and specific to Decoy.

## 3. Design notes

One rule per concern, enforced at one choke point with a guard test. No new `os.name` or
`sys.platform` check outside the choke points named here; a census sentry in each repo counts them
(D9).

- **D1 Engine import (EW1).** One module, `E:fileaccess/_osflags.py`, defines every POSIX-only open
  flag the engine uses, with a Windows value (`O_CLOEXEC` maps to `O_NOINHERIT`; `O_DIRECTORY`,
  `O_NOFOLLOW`, `O_NOCTTY` and `O_NONBLOCK` map to 0 and no win32 arm relies on them), and one
  `WINDOWS` constant. `resource` is imported inside the isolated route's POSIX arm only. Guard:
  `ET:sentry/test_win32_import_surface.py` parses every engine module (AST, with import aliases
  normalized, recurring-defects class 5) and fails on a module-scope
  `import resource|fcntl|pwd|grp|termios` outside a `try`/`except ImportError`, a module-scope
  `os.O_<posix-only>` read outside `_osflags.py`, or a module-scope `ctypes.CDLL(None)`.
  `RootedFileAccess` construction on win32 raises `FileAccessUnavailable` for the default and the
  `allow_portable_fallback=True` forms (F22 section 0 row C1).
- **D2 Engine locks, scratch and process kill (EW2).** One lock primitive per repo. Engine:
  `E:fileaccess/_oslock.py` `try_lock(fd, *, shared: bool)`: POSIX `flock`; Windows
  `msvcrt.locking` for exclusive, and `LockFileEx` through `ctypes` only if R0 shows a shared lock is
  needed on Windows. `_durable._held_lock`, `_scratch.py:174` and the F22 publication lock all call
  it. One process-kill helper, `E:execution/_proc_kill.py` `hard_kill(pid)`: POSIX `SIGKILL`,
  Windows `os.kill(pid, signal.SIGTERM)`. Out-of-core scratch goes through the protected allocator,
  which already has the Windows DACL arm. Guard: the D9 census, plus an AST rule that `fcntl.flock`
  and `msvcrt.locking` appear only in `_oslock.py`.
- **D3 Publication (EW3 = F22 w1).** Built as F22 revision 11 section 5.8 states, with one change:
  the lock calls D2's `try_lock` instead of a second `msvcrt` call site. Bind is `os.rmdir` of an
  empty leaf then an exclusive `os.rename` with the bounded retry; files flushed with `os.fsync`; no
  directory durability (L1w); the isolated route refuses at its entry on win32.
- **D4 Private files (EW4, CW1).** The engine's DACL code is the one implementation. EW4 exports
  three small public functions from `decoy_engine.fileaccess`: `create_owner_only_file(path) -> int`
  and `create_owner_only_dir(path) -> None` (POSIX: `O_EXCL|O_NOFOLLOW` 0600 and `mkdir` 0700 then an
  explicit mode, as today; Windows: `_win_create_file` and `_win_create`), and
  `owner_only_ok(path) -> bool` (POSIX mode bits; Windows the DACL read back). They are labelled
  experimental (row EXPERIMENTAL-TIER) because only the CLI uses them. EW4 also gives the engine's
  private output labels (`isolated` used by `write_private`, `vault_direct`, `quarantine`) their
  win32 stage arm through the same functions. The CLI's `_private_file` Windows arm (CW1) calls
  these three functions and nothing else (recurring-defects class 6: public API only). Guard: the
  CLI sentry `CT:sentry/io_policy/test_private_files.py` gains a rule that no CLI module calls
  `ctypes`, `win32security` or `icacls`.
- **D5 CLI locks (CW1).** `C:_private_file.py:224` `try_lock_exclusive` gains the `msvcrt.locking`
  arm and `advisory_lock_available()` (`:219`) returns True on Windows. Every CLI lock already goes
  through it (`C:distribution/lock.py:46-60`, the vault lock, `publish_local_targets`). A lock on a
  directory descriptor (POSIX `publish_local_targets`) becomes, on Windows only, a lock on a fixed
  hidden file `.decoy-publish.lock` in that folder, because `os.open` cannot open a directory on
  Windows.
- **D6 Runtime pointer and launcher (CW2).** `C:distribution/layout.py` owns the pointer through
  three functions: `point_current_at(slot)`, `read_current_slot()` and `interpreter_path(slot_dir)`.
  POSIX keeps the symlink and `python/bin/python3`. Windows writes `<home>\current.txt` holding the
  slot name only, through `_atomic.write_atomic` (atomic replace with the bounded retry), and the
  interpreter is `python\python.exe`. The PATH launcher on Windows is `<home>\bin\decoy.cmd`, with
  fixed text: `@echo off`, `setlocal`, `set /p DECOY_SLOT=<"%~dp0..\current.txt"`,
  `set PYTHONUTF8=1`, `set PYTHONDONTWRITEBYTECODE=1`, then
  `"%~dp0..\versions\%DECOY_SLOT%\python\python.exe" -I -B -m decoy %*`, then
  `exit /b %ERRORLEVEL%`. Its text never names a version, so an upgrade never rewrites it, and the
  known hazard of `cmd.exe` reading a batch file that changes while it runs cannot occur. The slot
  name is checked by the existing slot rule (`layout.slot_version`, anchored, recurring-defects
  class 1); a bad `current.txt` makes the reader refuse, and the launcher fails closed because the
  `python.exe` path does not exist. Guard: an AST rule fails on `os.readlink`, `os.symlink`,
  `replace_symlink` or `current_link()` anywhere under `C:distribution/` except the three layout
  functions. `install.ps1` already calls `python -I -B -m decoy.distribution.layout_point <slot>`,
  so install and upgrade share one pointer writer.
- **D7 Upgrade and prune (CW3).** A slot is removed in two steps: rename it to
  `versions\.trash-<slot>-<token>` (Windows refuses the rename while any file inside is in use), then
  delete the trash directory. A refused rename leaves the slot whole and valid and is reported as
  `deferred` in the upgrade summary; a later `decoy upgrade` retries it. A trash directory that
  fails to delete part way is never a slot (the slot rule rejects its name) and is retried next run.
  Same-version repair (`decoy upgrade --force`) when the running slot is the superseded one: the new
  `+<build>` slot goes live and the running one is deferred. The rename-then-delete form is used on
  both OSes so there is one code path (it is correct on POSIX too). Guard: an AST rule that
  `shutil.rmtree` under `C:distribution/` is called only from the trash remover.
- **D8 Bundle and release (CW4).** `PT:build_bundle.py` gets one per-target layout table:
  interpreter path, `site-packages` path, launcher kind (`sh` for POSIX, none for Windows), shebang
  normalization on or off. The Windows bundle stays a `.tar.gz` with a top-level directory and
  `BUNDLE_INFO.json`. A build-time check refuses the Windows bundle if any member's relative path
  is longer than 150 characters or if two members differ only by case (Windows would merge them).
  `release.yml` gains a fourth build leg on a GitHub-hosted `windows-2022` runner (ephemeral, as the
  hosted `macos-14` leg is) that runs `stage` only; signing stays in the Linux `sign` job. If Q3 is
  yes, the `sign` job Authenticode-signs `install.ps1` with `jsign` before the Ed25519 and SSHSIG
  pass (Authenticode changes the bytes, so it comes first).
- **D9 One platform census per repo.** CLI `CT:sentry/test_platform_checks.py` and engine
  `ET:sentry/test_platform_checks.py` walk every module's AST and count `os.name`, `sys.platform`
  and `platform.system()` reads per module against a committed baseline that may only shrink. New
  reads are allowed only in the choke-point modules of D1 to D6. The baseline is written by the
  slice that adds the sentry (EW1 engine, CW1 CLI) at the count on its base head; no slice raises
  it. The walk is proved by a seeded read in a scratch copy (cross-cutting rule).
- **D10 Installer verifier (CW5).** `install.ps1` ports MAC-V1a's design notes 1 to 11 to
  PowerShell: `Select-Verifier` runs before any download; candidates are `$env:DECOY_OPENSSL` alone
  if set, else `openssl` on PATH, else `$env:SystemRoot\System32\OpenSSH\ssh-keygen.exe`, then
  `ssh-keygen` on PATH; each must pass its known answer (the RFC 8032 vector for OpenSSL, a fixed
  SSHSIG vector for `ssh-keygen`) before it is trusted; `Verify-File` is the only function that
  checks a signature; no usable candidate is exit 69 with `tried:` lines and the fix text
  (`Settings > System > Optional features > OpenSSH Client`, or Git for Windows). The pinned
  `PINNED_SSH_PUBKEY` is injected and checked by `sign_release.py inject-keys` and `check-keys`,
  extended to the `.ps1` placeholder. The user PATH (HKCU) gains `<home>\bin` unless
  `-NoModifyPath` (Q8). An ARM64 host refuses before any download (Q2).

Design principles that apply: one module per concern (each Windows rule changes in one place), and
dependency direction (the CLI uses the engine's public owner-only functions, never its private
modules). No new abstraction beyond the three layout functions, the lock and kill helpers, and the
three owner-only functions.

## 4. Behavior

### 4.1 Install (G1)

1. The user runs the one-liner. `install.ps1` selects a verifier, then downloads `version.json` and
   its sidecar, verifies, downloads the bundle and its sidecar, checks the SHA-256 and the signature.
2. `tar.exe` extracts into `versions\.incoming.<guid>`; the bundle's own interpreter runs
   `verify_extracted` and `selfcheck` (the native companion loads and its ABI matches).
3. The identity check, then `Move-Item` to `versions\<v>`, then `layout_point <v>` writes
   `current.txt`.
4. `bin\decoy.cmd` is written if absent (fixed text); HKCU PATH is updated unless `-NoModifyPath`.

### 4.2 Run (G2)

`decoy.cmd` reads `current.txt` and runs `python.exe -I -B -m decoy` in UTF-8 mode. The engine
imports (EW1), publishes output through the Windows arm (EW3), private stages get the protected DACL
(EW4), and locks hold (EW2, CW1).

### 4.3 CI lane (row 6)

A self-hosted runner, labels `[self-hosted, windows, x64, decoy-win]`, on a GCP Windows Server 2022
VM that the owner creates (Q5). A `windows-lane` job in each repo's existing `ci.yml`:

- Triggers: `pull_request` from branches of the same repository only (never forks: a self-hosted
  runner must not run untrusted code), when the diff touches the path set below;
  `workflow_dispatch`; nightly on `main`.
- Engine set: `ET:fileaccess/` (including `protected_dir/`), `ET:sentry/test_win32_import_surface.py`,
  the publication and vault tests EW3 names, the governor tests, and a new
  `ET:windows/test_import_all.py` (imports every engine module through `pkgutil.walk_packages`).
- CLI set: `CT:unit/private_file/`, `CT:e2e/private_file/`, `CT:unit/distribution/`,
  `CT:unit/library/`, `CT:sentry/test_atomic_writer.py`, plus the demo smoke: a fresh venv from the
  candidate wheels, `decoy --version`, `decoy doctor`, `decoy demo --json`, the quickstart, and a
  byte compare of the demo and quickstart output against the Linux golden (Q6).
- Path set: engine `fileaccess/`, `publication/`, `execution/_governor_monitor.py`,
  `execution/_isolated_*`, `execution/out_of_core/_scratch.py`, `vault.py`; CLI `_private_file.py`,
  `_atomic.py`, `distribution/`, `packaging_tools/`, `cli/demo.py`, `cli/library/`.
- Idle stop: the VM stops when idle through `~/bin/vm-reap`; a queued `decoy-win` job starts it
  with the same watcher pattern the gate VMs use. Never stop it while the runner is busy.
- No hidden failures (recurring-defects class 7): no `continue-on-error`, and the job fails when a
  test marked `windows` is skipped on the Windows runner (AT-LANE-1).

The lane result counts toward T1 and the T2 gate set for the touched units. It is not a T3 full
suite. A Windows full suite is Later (L-W8).

### 4.4 Release (row 94)

`release.yml` stages four bundles (Linux x86_64, Linux aarch64, macOS arm64, Windows x86_64), signs
in one Linux job, and the G6 canonical smoke installs the Windows candidate on the lane VM and on a
stock Windows 11 machine (Q4). Rollback for Windows users is the same as for the others: the version
document points back (REL-WEB rollback mode) and `decoy upgrade --rollback` returns to the retained
slot (AT-CW3-1). No data migration is involved.

## 6. Enumerations

### 6.1 Exit paths

- Install refusals: no verifier (exit 69, CW5); bad signature or checksum (exit 1, texts unchanged

  (`C:_private_file.py:67`), raised as `PrivateFileError` (`C:_private_file.py:77`).

## 14. Pre-mortem

- **Time.** About 3,900 lines. With Q1 (a), the engine half (about 1,870 lines) lands before the
  freeze and the CLI half (about 2,000 lines) fits 2026-12-04 to 2026-12-15 with two builders in
  parallel (CW1, CW2 and CW5 do not depend on each other). With Q1 (b) the window is too short for
  both halves plus a patch release. Q7 is the cut line.
- **R0 finds more.** The census is static. Likely extra finds: text-mode newline translation in a
  writer (F8), a dependency without a Windows wheel at our pins, Defender scanning a 600 MB bundle
  extraction slowly enough to look hung. Each becomes a row; a blocker outside these slices goes to
  the owner, as the row text requires.
- **The built-in `ssh-keygen` lacks `-Y`.** Some Windows 10 builds ship an older OpenSSH. That host
  gets exit 69 with the fix text; Windows 11 is the supported client (Q4).
- **Self-hosted runner trust.** A self-hosted runner must not run fork code. The lane runs only for
  same-repository branches, `workflow_dispatch` and the nightly schedule (4.3).
- **A stopped VM looks green.** The start-on-queue watcher and the nightly run make a missing result
  visible; node-watch reports a queued `decoy-win` job.
- **POSIX regression from a win32 arm.** Every slice runs the existing Linux and macOS suites for
  the touched units; D9 forbids new platform checks outside the choke points.
- **Cross-plan collision.** Row 47 moves `installer.py`; CW2 and CW3 are planned against the split
  modules and wait for 47-B. CLI-REL S0 owns `release.yml`; CW4 adds one leg after S0 merges.
- **Upgrade from an older Windows install.** None exists (Windows was gated off), so there is no
  migration from a symlink `current` on Windows.

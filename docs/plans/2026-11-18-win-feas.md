## 0. Summary for the owner

The bar (owner 2026-11-18): a user downloads the signed CLI bundle from the download page, installs
it on Windows, and `decoy demo` plus the basic quickstart run work end to end.

What stands between main and that bar (section 1.3 lists every site; R0 confirms on Windows):

1. **The engine does not import on Windows.** Module-scope POSIX names fail at import. Many more
   POSIX-only names sit inside functions and fail at call time.
2. **Every engine run that writes output fails on Windows.** F22 publication refuses on win32
   (`E:fileaccess/_local.py:536`). F22 w1 moves into 1.0 as EW3 (Q10, decided).
3. **Output bytes would differ on Windows.** `os.open` defaults to text mode on Windows, and pandas
   `to_csv` writes `os.linesep` (CRLF) unless told otherwise. Q6 (decided) promises the same masked
   data bytes on every OS.
4. **Scratch, auto-chunk and out-of-core use directory descriptors**, which Windows does not have.
   Large tables would fail. EW5 gives `ScratchArena` a Windows arm (Q11).
5. **The installer and runtime layout are POSIX-shaped**: a symlink `current`, a shell launcher, no
   lock, `openssl` required, and the upgrade check runs `current/decoy`.
6. **Private files inherit their folder's ACL on Windows** in the CLI.
7. **Path names Windows forbids** (`con`, `a:b`, trailing dot) pass the engine's component rule.

The plan: R0 records the failures on the Dell, then 15 build slices (6 engine, 8 CLI, 1 setup) and an
engine release on the existing train. Each slice is under 800 lines and fixes one concern at one
choke point. Total about 6,800 lines including tests, about 2,500 of them production code.

Timing: the engine slices land before the D-4 engine tag (Q1, decided). EW1's static half, EW6 and
CW8 do not need Windows to build and can start now. The CLI slices run from 2026-12-04, target
2026-12-15, cut line 2026-12-22 (Q7, decided).

## 1. FRAME

### 1.1 Problem

Windows is in 1.0 (owner 2026-11-18, CLI `docs/roadmap/decisions.md:13-15`). No part of the lifecycle
has run on Windows (`docs/distribution/decisions/2026-10-26-windows-target-gated.md`, "Context"; LIB
records say "Windows: NOT RUN (no runner)", `docs/records/lib-l1b3-evidence.md:110`).

### 1.2 Guarantee (what 1.0 promises on Windows)

On Windows 11 23H2 or later, x64, with Windows PowerShell 5.1 and no extra tools installed (Windows
10 22H2 is best effort, Q4):

- G1 Install. The PowerShell one-liner installs the signed bundle. The installer verifies the version
  document and the bundle signature before extraction, with no `openssl` on the machine. A failed or
  impossible verification refuses and installs nothing. The installer script itself is not
  Authenticode-signed in 1.0 (Q3).
- G2 Demo and quickstart. `decoy --version`, `decoy doctor`, `decoy demo` and the quickstart exit 0
  and write masked data files with the same bytes as Linux for the same input, key and config (Q6).
  Reports and descriptors carry paths and timestamps and are not byte-compared.
- G3 Upgrade and rollback work while the old version is running and never delete files from a
  version that a running `decoy` uses.
- G4 Private files. Every file and directory the CLI or engine creates as private is created with a
  protected DACL that grants the current user and SYSTEM only, from its first instant, or the
  operation refuses.
- G5 Locks. Install, vault and publication locks exclude a second process on Windows.
- G6 Names. A file name Windows cannot hold is refused with the existing component denial before
  any write.
- G7 Typed refusals. Every feature not Windows-capable in 1.0 refuses with a registered code before
  any write (section 5).

Non-goals (1.0): ARM64 (refused, Q2); the strict file-access policy; the isolated route; directory
durability (F22 L1w); an `.exe` launcher; Authenticode; MSI, winget or scoop; paths over 259
characters; full test suites on Windows.

### 1.4 Failure modes this plan designs against

- F1 A Windows install that looks verified but is not.
- F2 An upgrade or prune that deletes files a running `decoy` uses.
- F3 A private file that exists for a moment with an inherited, broader ACL.
- F4 Two upgrades or two publishers at once because a Windows lock arm is a no-op.
- F5 A path over 260 characters inside the bundle or staging folder.
- F6 A POSIX regression from a win32 arm, including any change to Linux output bytes.
- F7 A scattered platform check that a later change misses.
- F8 Output bytes that differ by OS (CRLF, 0x1A, encoding).
- F9 A release that claims Windows while the Windows jobs are red or not run.
- F10 A name Windows maps to a device or a stream (`nul.csv`, `out.csv:x`).

### 1.5 Demo and quickstart routes

Checked by reading: the demo config (`C:cli/demo.py` `_build_pipeline_yaml`) declares no casts, no
subset and no generation, and its sample is far below the auto-chunk row threshold
(`E:execution/_pipeline_chunk_route.py:44`), so the demo runs the sequential route and binds through
`publish_unit`. The quickstart on a user's own data can pass the threshold and take auto-chunk, and
a hold-back can spill into `ScratchArena`. R0 records the route stamp
(`quality_metrics["chunked_route"]`) for both. That is why EW5 is in 1.0 (Q11).

## 2. Established solutions (survey)

Searches run: web searches on Windows atomic replace, Artifact Signing, the OpenSSH client shipped
with Windows, uv's PowerShell installer, and pip cross-platform installs; codebase searches in both
repos for `os.name`, `sys.platform`, `fcntl`, `msvcrt`, `ctypes`, SDDL, `os.replace`, `symlink`,
`killpg`, `resource`, `dir_fd`, `fchmod` and `to_csv`.

Probe on the Dell (`dell-win`, 2026-11-18, read-only plus one known-answer check in `%TEMP%`,
cleaned up): Windows 11 build 10.0.26300; Windows PowerShell 5.1.26100; `OpenSSH_for_Windows_9.5p2`
at `C:\Windows\System32\OpenSSH\ssh-keygen.exe`; `tar.exe` at `C:\Windows\System32\tar.exe`;
`LongPathsEnabled` 0; `python` on PATH is only the Store alias. An SSHSIG made on Linux with an
`allowed_signers` line carrying `namespaces="decoy-release"` verified with exit 0, and a one-byte
change failed with a non-zero exit, when run through `Start-Process -RedirectStandardInput`. One
earlier probe that used a `cmd /c ... < file` or a PowerShell pipe hung and left `ssh-keygen`
holding the file; CW5 therefore uses `Start-Process` with a file redirect and a timeout (finding M9).

- **Atomic replace.** `os.replace` is `MoveFileExW(MOVEFILE_REPLACE_EXISTING)`: atomic for a file on
  one NTFS volume, but it fails while another handle lacks `FILE_SHARE_DELETE`. Git for Windows
  `mingw_rename` retries for a short bounded time. The CLI already does this once
  (`C:_atomic.py:532`, 950 ms); F22 5.8 uses the same. A directory bind is an exclusive `os.rename`
  onto an absent name.
- **Running executables.** rustup and uv (`self-replace`) rename a running exe aside and delete it
  later. Decoy never replaces a running file: versions live in their own folders and a pointer
  changes. Whether a folder rename is refused while a process runs from it depends on share modes,
  so Decoy does not rely on it: a running process holds a lock on its own marker (D7), the pattern
  of a pid lock file used by package managers such as pacman (`db.lck`) and Nix GC roots, made
  crash-safe with an OS lock instead of a pid.
- **Pointer without symlinks.** A symlink needs privilege; a junction cannot be replaced atomically;
  a pointer file replaced with `os.replace` can. The CLI already uses this pattern for the run
  folder's `latest` pointer on Windows (`C:cli/io/_layout.py:620-628`).
- **Owner-only ACLs.** A protected DACL set at creation through `SECURITY_ATTRIBUTES`
  (`CreateFileW`, `CreateDirectoryW`), never after. The engine has it
  (`E:fileaccess/_protected_dir.py:366-407`). Compare SIDs in binary with `EqualSid`; SDDL text
  aliases well-known SIDs (`BA`, `LA`), so string compares fail for administrators (finding M3).
  `GetVolumeInformationW` reports `FILE_PERSISTENT_ACLS`; FAT and exFAT lack it and are refused.
- **Locks.** `filelock` and `portalocker` use `msvcrt.locking(fd, LK_NBLCK, 1)` on a dedicated lock
  file; the OS releases it when the handle closes or the process dies.
- **Binary I/O.** On Windows `os.open` is text mode unless `os.O_BINARY` is set (CPython docs,
  `os.open` flags); text mode turns `\n` into `\r\n` on write and stops a read at 0x1A. pandas
  `DataFrame.to_csv` defaults `lineterminator` to `os.linesep`. Python's `newline` argument and
  UTF-8 mode (`-X utf8`, PEP 540) are the standard controls. Ruff `PLW1514`
  (`unspecified-encoding`) flags `open` and `write_text` without an encoding.
- **Windows names.** CPython 3.13 `os.path.isreserved` (`Lib/ntpath.py`) lists device names and
  trailing dot and space; the CLI already follows it (`C:_atomic.py:121-130`).
- **Cross-platform wheel install.** `pip install --target <dir> --platform win_amd64
  --python-version 3.10 --implementation cp --only-binary=:all:` installs Windows wheels from Linux
  (pip docs, "--platform"). The native companion wheel comes from the engine's Windows build.
- **Installer.** uv and rustup ship a PowerShell installer run with `irm <url> | iex` and add a user
  PATH entry in HKCU. Windows 10 1803 and later ship `tar.exe`. Windows PowerShell 5.1 has no
  Ed25519, so the verifier follows MAC-ED25519: OpenSSL if present, else built-in OpenSSH
  `ssh-keygen -Y verify` (OpenSSH 8.1 or later; the Dell has 9.5).
- **Signing.** Authenticode is not needed for the bar: a file fetched by `Invoke-WebRequest` and
  unpacked by `tar.exe` carries no Mark-of-the-Web, so SmartScreen does not prompt. A user who
  downloads `install.ps1` in a browser gets the Mark-of-the-Web, and the default `RemoteSigned`
  policy refuses an unsigned downloaded script; the docs give the one-liner and `Unblock-File`
  (Q3, decided: unsigned in 1.0).

Custom code left: the pointer reader and launcher, the in-use marker, the path budget, the
PowerShell verifier selection (a port of MAC-V1a), the path-based `ScratchArena` arm, and small lock
arms. Each is specific to Decoy and small.

## 3. Design notes

One rule per concern, one choke point, one guard test. No new platform check outside the modules
D9 allows.

- **D1 Engine flags and binary mode (EW1).** `E:fileaccess/_osflags.py` is the only module that
  reads `os.O_*`. It exports every open flag the engine uses, a `WINDOWS` constant, and
  `POSIX_NAME` (a map from each exported name to its `os.O_*` name). On Windows, POSIX-only flags
  are 0 and `O_BINARY | O_NOINHERIT` is added to every exported open-mode flag (`RDONLY`, `WRONLY`,
  `RDWR`); on POSIX the values equal `os.O_*` exactly. `resource` is imported inside the isolated
  route's POSIX arm. Guard `ET:sentry/test_win32_import_surface.py` (AST walk of every engine
  module, import aliases normalized per recurring-defects class 5) fails on: a module-scope or
  function-scope `os.O_*` read outside `_osflags.py`; a module-scope `import
  resource|fcntl|pwd|grp|termios` outside `try`/`except ImportError`; a `signal.SIG*` name that
  Windows lacks; `os.fchmod`; `os.geteuid`; a `dir_fd=` keyword; each outside its allowed module
  list. Recorded exceptions with reasons: `_governor_monitor.py` `SIGKILL` (isolated route only),
  `_openat2.py` (Linux only), `_rooted.py` `dir_fd` (strict policy, refused on win32), and the
  POSIX arms of `_local.py`, `_durable.py`, `_scratch.py` and `_protected_dir.py` that sit behind
  `_osflags.WINDOWS`. The engine private-file sentry (P1 in `ET:sentry/.../test_private_files.py`,
  the rule that private opens carry `O_NOFOLLOW` and `O_EXCL`) resolves `_osflags.X` through
  `POSIX_NAME` to the same rule, so a seeded open that drops `_osflags.O_NOFOLLOW` still fails (finding M6).
  `RootedFileAccess` construction on win32 raises `FileAccessUnavailable`.
- **D2 Engine locks and durability (EW2).** `E:fileaccess/_oslock.py` `try_lock(fd, *, shared)`:
  POSIX `flock`; Windows `msvcrt.locking` exclusive. R0 decides whether the one shared lock
  (`E:fileaccess/_scratch.py:174`) must be shared on Windows; if so, `LockFileEx` through `ctypes`
  in this module only. `_durable` skips directory fsync on win32 (L1w) and drops the `geteuid`
  chain walk there. No process-kill helper (finding M5): the only `SIGKILL` user is the isolated route,
  which refuses on win32.
- **D3 Publication (EW3 = F22 w1).** As F22 revision 11 section 5.8, with the lock through

## 4. Behavior

### 4.1 Install (G1)

1. The user runs the one-liner. `install.ps1` selects a verifier, downloads `version.json` and its
   sidecar, verifies, downloads the bundle and its sidecar, checks the SHA-256 and the signature.
2. `$env:SystemRoot\System32\tar.exe` extracts into `versions\.incoming.<guid>`; the bundle's
   interpreter runs `verify_extracted` and `selfcheck`.
3. Identity check, `Move-Item` to `versions\<v>`, then `layout_point <v>` writes `current.txt`.
4. `bin\decoy.cmd` is written if absent; HKCU PATH gains `bin` unless `-NoModifyPath`.

### 4.2 Run (G2)

`decoy.cmd` reads `current.txt` and runs `python.exe -I -B -X utf8 -m decoy`. The process takes its
in-use marker, the engine imports, output publishes through EW3, private stages get the protected
DACL, scratch goes through EW5, and locks hold.

### 4.3 Windows lane on the Dell (row 6)

No GitHub runner (owner Q5). The Dell `192.168.4.25` runs Windows 11 Pro (`ssh dell-win`, user
`louis`, admin key, never sleeps) and, in WSL2, the Linux node `dell-wsl` that hosts engine CI
runners.

- `~/bin/win-run <repo> <sha> <job>` (WR): ssh to `dell-win`, fetch the exact SHA into a short
  checkout root (`C:\dc\<repo>`, short to save path length), build the venv from Python 3.10.20
  (python-build-standalone through `uv`, because python.org ships no Windows installer after
  3.10.11), install from the lock, run the named job with a 15-minute stall guard, and copy back a
  log whose first line is the SHA and whose last line is `EXIT n`. A lock on the Dell allows one
  Windows job at a time. Read the result by the `EXIT` line and failing test ids, never by a
  summary line.
- Jobs (the "lane"): `engine-win` (engine `ET:fileaccess/`, `ET:windows/`, the publication, vault,
  scratch and out-of-core tests the EW slices name, the import walk and the 0x0A, 0x0D, 0x1A
  round-trip); `cli-win` (`CT:unit/private_file/`, `CT:e2e/private_file/`, `CT:unit/distribution/`,
  `CT:unit/library/`, `CT:sentry/test_atomic_writer.py`); `demo-win` (fresh venv from the candidate
  wheels, `decoy --version`, `doctor`, `demo --json`, the quickstart, and a hash compare of the
  masked data files against the Linux golden). The Linux golden is made from the same SHA in the
  same `win-run` call on `dell-wsl` (through `vm-run`'s Dell target), so both sides run one head
  (finding M10).
- When: on every slice that touches the path set (engine `fileaccess/`, `publication/`,
  `declared_casting/_quarantine_local.py`, `execution/_isolated_*`, `execution/out_of_core/`,
  `execution/_pipeline_auto_chunk.py`; CLI `_private_file.py`, `_atomic.py`, `distribution/`,
  `packaging_tools/`, `cli/demo.py`, `cli/io/_targets.py`, `cli/library/`, `cli/upgrade.py`), on
  the exact gate head and again on the merge head; and nightly on both `main` heads through a cron
  entry. node-watch reports a queued or stalled Windows job.
- Evidence: the gate record names the SHA, the job and the `EXIT` line. A Windows job that did not
  run is "not run", never green.
- Elevation: Windows OpenSSH gives an administrator a full token, so `win-run` jobs run elevated.
  WR creates a standard local user `decoyci` on the Dell for the non-elevated cells (AT-EW4-5); R0
  confirms the elevation state.
- Memory: the Dell's WSL engine CI runners share the box. `win-run` checks free memory before it
  starts (the same threshold as node-watch) and queues when it is short.

The lane counts toward T1 and the T2 gate set for the touched units. It is not a T3 suite (L-W8).

### 4.4 Release (row 94)

`release.yml` stages four bundles; the Windows stage is assembled on Linux (D8). Signing stays in
the Linux `sign` job. G6 installs the Windows candidate on the Dell through `win-run` and on a
Windows 11 evaluation VM on pve2 by hand (Q4). Rollback for Windows users is the same as for the
others: the version document points back and `decoy upgrade --rollback` returns to the retained
slot.

## 1. FRAME

### Problem

`install.sh` checks two raw Ed25519 signatures (the version document and the bundle) with
`openssl pkeyutl -verify -pubin -rawin` (`install.sh` lines 103 to 112). Two kinds of supported host cannot
run that command:

1. **Stock macOS.** `/usr/bin/openssl` is LibreSSL 3.3.6 (checked on the Mac mini, macOS 15.1, 2026-11-15).
   It cannot load an Ed25519 public key: `unable to load Public Key ... unsupported algorithm`. LibreSSL added
   Ed25519 to its EVP interfaces only in 3.7.0. `macos-arm64` is a supported target.
2. **Linux with OpenSSL 1.1.1.** `-rawin` does not exist in OpenSSL 1.1.1 (`apps/pkeyutl.c` on the
   `OpenSSL_1_1_1-stable` branch has no `rawin`; the 3.0 branch has it). The supported Linux floor is
   glibc `manylinux_2_28` (`docs/install.md:37`), which includes RHEL 8 (OpenSSL 1.1.1k), Debian 10 and
   Ubuntu 20.04 (1.1.1f).

On both, `verify_sig` returns non-zero and the installer says "version-document signature INVALID --
refusing (possible tampering)" (`install.sh` line 244) or "bundle signature INVALID" (line 330). The user
cannot install, and the message is wrong: it blames tampering for a missing capability. `need openssl`
(line 150) checks only that some `openssl` exists.

A second effect: the shell-installer tests gate on `shutil.which("openssl")`
(`tests/unit/test_distribution_acceptance.py:113`). On a host with only LibreSSL, a test that expects a
refusal for another reason can pass because the signature check refused first; for example
`tests/unit/test_distribution_r7_security.py:341` expects "signature INVALID" and gets it for the wrong reason.

### Guarantee

- On a host with an Ed25519-capable `openssl` anywhere the installer looks, the install works as today, with
  the same checks in the same order.
- On a host with none, the installer refuses **before any download**, exits with its own code (4), says it
  **cannot verify** (never "INVALID" or "tampering"), names what it tried, and prints the fix.
- "Signature INVALID" is printed only after a verifier has proved, on a known-answer test, that it can tell a
  good Ed25519 signature from a bad one.
- Fail-closed holds: no route lays down a bundle without a passing signature check by a verifier that passed
  the known-answer test.

### Non-goals

- No change to the signing scheme, the release key, the version document or `decoy upgrade` (which verifies
  in the bundled Python with `cryptography` and is not affected).
- No change to `install.ps1` (Windows is gated off this cycle; it has the same `openssl` dependency, see FU-3).
- No downloaded or bundled verifier binary in this slice (option B, rejected for V1 below).
- No hand-rolled Ed25519 in shell, awk or Perl.

### Failure modes

- F1. No candidate `openssl` at all: refuse with exit 4 and the fix.
- F2. Candidates exist but none passes the known-answer test (LibreSSL 3.3.6, OpenSSL 1.1.1, a broken shim):
  refuse with exit 4, list each tried path with its `version` line.
- F3. A candidate that accepts every signature (a shim that always exits 0): the negative half of the
  known-answer test fails it; it is never used.
- F4. `DECOY_OPENSSL` names a missing or incapable binary: refuse with exit 4. No silent fallback to PATH,
  because the user asked for that one.
- F5. A capable verifier and a corrupted signature: exit 1, "signature INVALID", as today.
- F6. The known-answer files must not outlive the run: they live in `$WORK`, which the existing EXIT trap
  removes.

Known-answer test source: RFC 8032 section 7.1, TEST 2 (public key `3d4017c3...af4660c`, message one byte
`0x72`, signature `92a009a9...12bb0c00`). Checked on OpenSSL 3.0.20 on 2026-11-15: the vector verifies and the
one-byte message `0x73` fails with the same signature.

**Recommendation: A in this slice.** It fixes the wrong message on every host, makes every Homebrew or
MacPorts Mac work without the user touching PATH, and makes OpenSSL 1.1.1 hosts fail with an accurate
message. It adds no new trust. It does not make a stock Mac with no package manager install: that needs C
(owner call, Q1) or B2 (V2).

## 3. Design notes

1. **Probe before any download.** The probe runs after `WORK` is created and the EXIT trap is set (line 209),
   before the pinned key is written and before the first `fetch`. `uninstall` and the existing-install
   refusal (lines 148 and 177) still need no `openssl`.
2. **One selected binary, used for every call.** `verify_sig` uses `"$OPENSSL"` for both the base64 decode
   and `pkeyutl`. `need openssl` (line 150) goes; the probe replaces it.
3. **Known-answer test, both halves.** `kat_ok BIN` writes the TEST 2 public key PEM, the message, a changed
   message and the base64 signature into `$WORK/kat/`, then requires `verify_sig` with `BIN` to pass on the
   message and fail on the changed one. A binary that accepts everything, or rejects everything, is not used.
4. **Candidate order.** If `DECOY_OPENSSL` is set it is the only candidate (F4). Otherwise: `openssl` on PATH,
   `openssl3` on PATH, then `OPENSSL_FALLBACKS`, one assignment line holding
   `/opt/homebrew/opt/openssl@*/bin/openssl /opt/homebrew/opt/openssl/bin/openssl /opt/homebrew/bin/openssl
   /usr/local/opt/openssl@*/bin/openssl /usr/local/bin/openssl /opt/local/bin/openssl
   /home/linuxbrew/.linuxbrew/bin/openssl`. Globs that match nothing are skipped. The first candidate that
   passes is used and the installer prints `verifier: <path> (<version line>)`.
5. **Trust.** Every candidate is a binary the user's account can already run; PATH reaches it today. A
   malicious binary that passes the known-answer test and lies about other inputs is outside the V1 threat
   model (accidental leaks only) and is no worse than a malicious `openssl` on PATH today. `DECOY_OPENSSL`
   names a verifier, not a trust anchor; the pinned key stays the only anchor and the existing rule that an
   environment variable cannot replace it is unchanged.
6. **The refusal.** Exit 4, never 1. stderr, one `decoy install:` line per item:
   `cannot verify Ed25519 signatures: no usable openssl was found. Nothing was downloaded or installed.`,
   `tried: <path> (<version line or "not runnable">)` per candidate, then the fix:
   `macOS: brew install openssl@3`, `RHEL 8: dnf install openssl3 (EPEL)`,
   `other Linux: OpenSSL 3.0 or newer`, `or name one: DECOY_OPENSSL=/path/to/openssl sh install.sh`.
   No "INVALID" and no "tampering" anywhere on this path.
7. **Exit codes.** Today every refusal is 1. The new code 4 is reserved for "cannot verify", so CI and the
   RG-S candidate smoke can tell a host problem from a bad bundle. Other refusals stay 1.
8. **Test gate.** The shell tests' skip gate (`needs_shell_tools`) becomes "an Ed25519-capable openssl", using
   the same known answer from Python, so a LibreSSL-only host skips them with a reason instead of passing them
   for the wrong reason. The new stock-macOS test runs exactly there.

## 5. Enumerations

### 5.1 Exit paths

- 0: installed, or `uninstall`, or `--help` (unchanged).
- 1: every existing refusal (unchanged; the `die` calls at `install.sh` lines 156 to 394), including
  "signature INVALID" on a proven verifier.
- 4 (new): no candidate passed the known-answer test (F1, F2, F3, F4). `docs/install.md:65` gains the
  sentence and the code.
- The RG-S candidate smoke maps any non-zero `install.sh` exit to `smoke_install_failed`
  (`packaging_tools/smoke_install.py` on `feat/rel-gate-s`); a distinct `smoke_verifier_missing` is FU-4.

### 5.2 Routes

- `DECOY_OPENSSL` set: that binary only.
- `openssl`, then `openssl3`, on PATH.
- `OPENSSL_FALLBACKS`, in the order of design note 4.
- None passes: exit 4.
- `decoy upgrade` is not a route here: it verifies in Python (`src/decoy/distribution/signing.py`), unchanged.

### 5.3 FK shapes

N/A: the installer reads no tables and writes no rows; there are no keys between records.

### 5.4 Fields

- `DECOY_OPENSSL` (new, optional): a path to an `openssl` binary.
- `OPENSSL_FALLBACKS` (new, a script constant, not an environment variable).
- The `verifier:` info line and the `tried:` lines (new stderr text).
- Existing fields unchanged: `DECOY_HOME`, `DECOY_BIN_DIR`, `DECOY_VERSION_URL`, `DECOY_RELEASE_PUBKEY_FILE`,
  `DECOY_LOCAL_BUNDLE` (`install.sh` lines 28 to 35).

### 5.5 Output surfaces

- stderr of `install.sh` only. The new lines name binary paths and `openssl version` output, never data
  values, keys or secrets. A `DECOY_OPENSSL` under the user's home shows that path on the user's own terminal.
- Docs: `docs/install.md:65` (requirement and exit 4), `packaging_tools/README.md:29` (verifier sentence).
  `docs/distribution/version-endpoint-contract.md:31` stays true (`openssl pkeyutl -verify -rawin`).
- No `--json`, no evidence, no log file.

## 7. Acceptance tests (red first)

New file `tests/unit/distribution/test_install_sh_verifier.py`. Shims are small `sh` scripts written by the
test into `tmp_path`. A test that needs to control the fallbacks runs a copy of `install.sh` with the single
`OPENSSL_FALLBACKS=` line rewritten, the same way `test_install_sh_ignores_override_when_key_is_pinned`
rewrites the key placeholder.

- AT-V1 (F2, exit path 4): PATH's only `openssl` is a shim that answers like LibreSSL 3.3.6 (`version`
  prints `LibreSSL 3.3.6`, `pkeyutl` prints "unable to load Public Key" and exits 1); fallbacks empty;
  `DECOY_VERSION_URL` is a `file://` path that does not exist. Expect exit 4, stderr contains "cannot verify"
  and "brew install openssl@3" and the `tried:` line with `LibreSSL 3.3.6`, contains neither "INVALID" nor
  "tampering", and `DECOY_HOME` was not created. Exit 4 rather than the fetch error (exit 1) proves the
  probe ran before any download.
- AT-V2 (F3): the shim's `pkeyutl` always exits 0. Expect exit 4.
- AT-V3 (route, fallback): PATH shim as AT-V1; fallbacks rewritten to a logging wrapper around the real
  `openssl`; a correctly signed version document of the wrong schema. Expect "version document signature
  verified", then the schema refusal (exit 1), and the `verifier:` line naming the wrapper.
- AT-V4 (F5, frozen): capable verifier, version-document signature corrupted. Expect exit 1 and
  "version-document signature INVALID". Same for `DECOY_LOCAL_BUNDLE` with a corrupted `.sig`: "bundle
  signature INVALID".
- AT-V5 (route, explicit): PATH shim as AT-V1, `DECOY_OPENSSL` set to the real `openssl`. Expect the
  signature to verify.
- AT-V6 (F4): PATH has the real `openssl`, `DECOY_OPENSSL` points at a missing file. Expect exit 4 and a
  `tried:` line for that path only.
- AT-V7 (stock macOS, real binary): runs only when `platform.system() == "Darwin"` and `/usr/bin/openssl
  version` starts with `LibreSSL 3.`. PATH `/usr/bin:/bin`, fallbacks empty. Expect exit 4 and the LibreSSL
  `tried:` line.
- AT-V8 (Mac, end to end, manual, recorded in the result): on the Mac mini with `/usr/bin` first on PATH,
  install the RG-S AT-S6 throwaway-key bundle set with `DECOY_LOCAL_BUNDLE` and `DECOY_OPENSSL` set to the
  Homebrew `openssl`. Expect a full install and `decoy --version`.
- AT-V9 (cleanup): after AT-V1's run, no `kat` directory remains and the count of entries in the test's
  `TMPDIR` is unchanged.
- AT-V10 (order): `uninstall` with a PATH that has no `openssl` exits 0; the existing-install refusal with no
  `openssl` still exits 1 with "refusing to overwrite".
- AT-V11 (gate): the shared `needs_shell_tools` gate in `tests/unit/test_distribution_acceptance.py:113`
  uses the known answer, and a unit test of the gate's helper returns False for the AT-V1 shim and True for
  the real `openssl`.
- AT-V12 (OpenSSL 1.1.1, manual, optional): in an `ubuntu:20.04` container on a GCP test VM, run the
  version-document path. Expect exit 4 with an `OpenSSL 1.1.1` `tried:` line. Recorded as not run if no
  container runtime is available; AT-V1 covers the logic.

Mutations (each must turn at least one AT red): M1 drop the negative known-answer half (AT-V2); M2 `die`

## 13. Pre-mortem

- P1. A Homebrew prefix the list misses (a custom prefix like `~/homebrew`): the user sees exit 4 with the
  fix and `DECOY_OPENSSL`. Accepted; the message names the escape.
- P2. LibreSSL 3.7 or newer passes Ed25519 in EVP but its `pkeyutl` may not take `-rawin`: the known answer
  decides at run time, never a version string.
- P3. OpenSSL 3.5 makes `-rawin` implied for EdDSA; it still accepts the flag, so one command serves 3.0 to
  4.x. The known answer catches a future change.
- P4. A test host with only LibreSSL silently skips the shell tests: AT-V7 runs exactly there and the
  gate's reason names the missing capability. The Mac CI runner user `decoyci` has no Homebrew; its skips
  are visible in the job summary.
- P5. The RG-S candidate smoke strips `DECOY_*` from the installed CLI's environment but runs `install.sh`
  with the caller's PATH; a Mac smoke still needs a capable `openssl` on PATH or under a fallback prefix.
- P6. Someone reads exit 4 as the CLI's exit 4. They are different programs; `docs/install.md` says the
  installer's codes in its own table.

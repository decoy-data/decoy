## 1. FRAME

### Problem

`install.sh` checks two raw Ed25519 signatures (the version document and the bundle) with
`openssl pkeyutl -verify -pubin -rawin` (`install.sh` lines 103 to 112). Two kinds of supported host cannot
run that command:

1. **Stock macOS.** `/usr/bin/openssl` is LibreSSL 3.3.6 (checked on the Mac mini, macOS 15.1, 2026-11-15).
   It cannot load an Ed25519 public key: `unable to load Public Key ... unsupported algorithm`. LibreSSL added
   Ed25519 to its EVP interfaces only in 3.7.0. `macos-arm64` is a supported target, and the owner requires a
   stock Mac to install in V1.
2. **Linux with OpenSSL 1.1.1.** `-rawin` does not exist in OpenSSL 1.1.1. The supported Linux floor is glibc
   `manylinux_2_28` (`docs/install.md:37`), which includes RHEL 8, Debian 10 and Ubuntu 20.04 (all 1.1.1).

On both, `verify_sig` returns non-zero and the installer says "version-document signature INVALID --
refusing (possible tampering)" (`install.sh` line 244) or "bundle signature INVALID" (line 330). The user
cannot install, and the message blames tampering for a missing capability. `need openssl` (line 150) checks
only that some `openssl` exists.

A second effect: the shell-installer tests gate on `shutil.which("openssl")`
(`tests/unit/test_distribution_acceptance.py:113`). On a LibreSSL-only host a test that expects a refusal for
another reason can pass because the signature check refused first
(`tests/unit/test_distribution_r7_security.py:341`).

### Guarantee

- A stock Mac (built-in `/usr/bin/openssl` without Ed25519, built-in `/usr/bin/ssh-keygen`, no Homebrew or
  MacPorts, no override variable) installs a released bundle. Both signatures are checked by
  `ssh-keygen -Y verify` against the pinned OpenSSH form of the release key.
- A host with an Ed25519-capable OpenSSL installs as today, with the same checks in the same order.
- A host with neither refuses **before any download** with exit 69 (`EX_UNAVAILABLE`), says it **cannot
  verify** (never "INVALID" or "tampering"), names what it tried and prints the fix.
- Every signature check goes through one function, `verify_file`. No path lays down a bundle without a
  passing check by a verifier that passed its known-answer test.
- "Signature INVALID" is printed only after the selected verifier has proved, on a known answer, that it
  tells a good signature from a bad one.
- The PEM and OpenSSH key forms in a released `install.sh` are the same key. A release with a mismatch or a
  leftover placeholder cannot be published.

### Non-goals

- No change to the existing `.sig` signatures, the release key, the version-document schema or
  `decoy upgrade` (which verifies in Python with `cryptography`).
- No change to `install.ps1` (Windows is gated off this cycle, see FU-3).
- No downloaded or bundled verifier binary (option B2, V2).
- No hand-rolled Ed25519 or SSHSIG framing. SSHSIG is made by `ssh-keygen -Y sign` and checked by
  `ssh-keygen -Y verify`.
- Building the CLI-REL S0 workflow. This plan defines what S0 must do (PRE-S0) and ships the signer
  subcommands S0 calls.

### Failure modes

- F1. No usable verifier (no OpenSSL 3, no `ssh-keygen` 8.1 or newer, or an OpenSSH key that is still the
  placeholder): exit 69, the fix, nothing downloaded.
- F2. Candidates exist but none passes its known-answer test (LibreSSL 3.3.6, OpenSSL 1.1.1, OpenSSH 8.0, a
  broken shim): exit 69, each tried path listed.
- F3. A candidate that accepts every signature: the negative half of its known-answer test fails it.
- F4. `DECOY_OPENSSL` names a missing or incapable binary: exit 69, no fallback.
- F5. A usable verifier and a bad signature (missing sidecar, wrong key, wrong namespace, signature of another
  file, changed bytes): exit 1 with the existing refusal text.
- F6. A verifier call inherits the script's stdin under `curl | sh` and eats the rest of the script: every
  call has stdin redirected from a named file (design note 3).
- F7. The PEM and OpenSSH forms in `install.sh` differ, or one is a placeholder: `check-keys` refuses at build
  and candidate time; at run time a mixed state (one form real, one placeholder) is exit 1.
- F8. A published candidate lacks a `.sshsig` sidecar or does not list it in `SHA256SUMS`: candidate
  completeness refuses it (PRE-S0).
- F9. Known-answer and allowed-signers files outlive the run: they live in `$WORK`, which the EXIT trap
  removes. The signer's temporary OpenSSH private key lives in a temp directory removed in a `finally`.

Known-answer sources. OpenSSL: RFC 8032 section 7.1 TEST 2 (public key `3d4017c3...af4660c`, message `0x72`,
signature `92a009a9...12bb0c00`); `0x73` must fail. SSHSIG: no published vector exists, so the builder makes
one fixed throwaway key and one signature over the one-byte message `0x72` with `ssh-keygen -Y sign`, and
commits the OpenSSH public key and the armored signature as constants in `install.sh`. The changed message
`0x73` must fail. AT-K4 re-checks the constants with the real `ssh-keygen` on every T1 run. The known-answer
key is not the release key and signs nothing else.

The stdin form of the commands was checked on OpenSSH 9.2p1 on 2026-11-15:
`ssh-keygen -Y sign -f k -n decoy-release < d > d.sshsig` writes only to stdout, and the verify command of
design note 4 exits 0 on `d` and 255 after one byte is appended. `-Y check-novalidate` on the same file does
not use the allowed-signers file, which is why it is never used.

**Recommendation: A and C together, behind one choke point.** A keeps today's path for hosts that have
OpenSSL 3. C makes a stock Mac install with no package manager. The two formats over one key cannot be
replayed as each other: SSHSIG signs a blob that starts with the magic `SSHSIG` and the namespace.

## 3. Design notes

1. **Select before any download.** `select_verifier` runs after `WORK` is created and the EXIT trap is set
   (line 209), before the pinned keys are written out and before the first `fetch`. `uninstall` (line 148)
   needs no verifier. The existing-install refusal (line 177) needs none after this change; today it needs
   `openssl` because `need openssl` (line 150) runs first. AT-V10 pins that change.
2. **One choke point.** `verify_file DATA_FILE SIDECAR_BASE` is the only function that checks a signature.
   It reads `$VERIFIER_KIND` (`openssl` or `sshsig`) and `$VERIFIER_BIN`, both set once by `select_verifier`.
   For `openssl` it checks `SIDECAR_BASE.sig` with the existing `verify_sig` body. For `sshsig` it checks
   `SIDECAR_BASE.sshsig` with the command in note 4. Any other `VERIFIER_KIND`, an empty one, or a missing
   sidecar returns 1. Both call sites (lines 244 and 330) call `verify_file` and keep their exact `die` text.
   No other line in `install.sh` runs `pkeyutl` or `-Y verify`; AT-X2 is the guard test.
3. **stdin.** No verifier call inherits the script's stdin. OpenSSL calls (`version`, `base64`, `pkeyutl`)
   read `< /dev/null`. `ssh-keygen -Y verify` reads the signed data from stdin, so it reads `< "$DATA_FILE"`.
   The `tried:` line for `ssh-keygen` shows its path and the known-answer result (not every `ssh-keygen` has a
   version flag). Every printed version line goes through `tr -cd '[:print:]'` and is cut to 80 characters.
4. **The SSHSIG command.** `select_verifier` writes one allowed-signers file, `$WORK/allowed_signers`, with
   exactly one line:
   `decoy-release@decoy.dev namespaces="decoy-release" ssh-ed25519 <base64 key blob>`
   where the key blob is `PINNED_SSH_PUBKEY`. The check is exactly:
   `"$VERIFIER_BIN" -Y verify -f "$WORK/allowed_signers" -I decoy-release@decoy.dev -n decoy-release -s "$DATA_FILE.sshsig" < "$DATA_FILE" > /dev/null 2>&1`.
   Exit 0 passes; anything else fails. The identity and the namespace are script constants, not environment
   input. `-Y check-novalidate` and `-Y find-principals` are never used: they do not bind the pinned key. The
   known answer uses the same command with its own allowed-signers file under `$WORK/kat/`.
5. **Selection order.** If `DECOY_OPENSSL` is set and not empty, it is the only candidate (F4); it must be an
   absolute path. Set but empty counts as unset. Otherwise: OpenSSL candidates first (`openssl` and
   `openssl3` on PATH, then the one `OPENSSL_FALLBACKS=` line: `/opt/homebrew/opt/openssl@*/bin/openssl
   /opt/homebrew/opt/openssl/bin/openssl /opt/homebrew/bin/openssl /usr/local/opt/openssl@*/bin/openssl
   /usr/local/bin/openssl /opt/local/bin/openssl /home/linuxbrew/.linuxbrew/bin/openssl`). The first that
   passes the RFC 8032 known answer is used with `VERIFIER_KIND=openssl`. If none passes: SSHSIG candidates
   (`ssh-keygen` on PATH, then `/usr/bin/ssh-keygen`), only when `PINNED_SSH_PUBKEY` is not the placeholder.
   The first that passes the SSHSIG known answer is used with `VERIFIER_KIND=sshsig`. Else exit 69. The
   installer prints `verifier: <kind> <path> (<version line>)`. There is no override variable for
   `ssh-keygen`; a stock Mac needs none.
6. **Two key forms, one key.** `install.sh` holds `PINNED_PUBKEY` (PKCS#8 PEM, placeholder
   `__DECOY_RELEASE_PUBLIC_KEY__`, as today) and a new `PINNED_SSH_PUBKEY` (the base64 `ssh-ed25519` blob,
   placeholder `__DECOY_RELEASE_SSH_PUBLIC_KEY__`). `ssh-keygen` cannot import the PEM key (checked), so both
   are pinned. `packaging_tools/sign_release.py` gains four subcommands:
   - `pubkeys --key <private.pem>`: derives both public forms from the one private key with `cryptography`.
   - `inject-keys --key <private.pem> --in install.sh --out <file>`: replaces both placeholders with the
     derived forms, then runs `check-keys` on the output and fails if it fails.
   - `check-keys <install.sh>`: decodes both pinned forms to their raw 32 bytes with `cryptography` and exits
     non-zero with a fixed message when they differ, when either still holds its placeholder, or when either
     does not parse.
   - `sshsig --key <private.pem> --in <file> --out <file>.sshsig`: writes the private key in OpenSSH format to
     a 0600 file in a fresh temp directory, runs `ssh-keygen -Y sign -f <tmpkey> -n decoy-release
     < <file> > <file>.sshsig` (stdin form, so it never writes `<file>.sig` and cannot clobber the raw
     signature), then removes the temp directory. Same key source as `sign` (`DECOY_RELEASE_KEY_FILE` or
     `DECOY_RELEASE_KEY_PEM`).
   At run time `install.sh` refuses with exit 1 when exactly one of the two forms is a placeholder
   ("release keys incomplete -- refusing"). Both placeholders is a dev build: `DECOY_RELEASE_PUBKEY_FILE` works
   as today for the OpenSSL route, and the SSHSIG route is not offered.
7. **Sidecars and URLs.** Every file signed today gets one more sidecar, `<file>.sshsig`, an armored
   `-----BEGIN SSH SIGNATURE-----` block. URLs follow the `.sig` convention:
   `https://decoy.dev/cli/version.json.sshsig` and `<artifact url>.sshsig`, that is
   `https://decoy.dev/cli/<version>/decoy-<version>-<target>.tar.gz.sshsig`. The version-document schema does
   not change: the bundle's `.sshsig` URL is the artifact `url` plus `.sshsig`, which is safe because the
   SSHSIG check itself proves the file. An `sshsig` artifact field was rejected because it changes the frozen
   `cli-version-document/v1` schema that `decoy upgrade` parses. For a pinned non-latest version the URL is
   the convention URL plus `.sshsig`, as `.sig` is today. The installer fetches only the sidecar its verifier
   needs. Offline `DECOY_LOCAL_BUNDLE` needs the tarball, `.sha256`, and the sidecar of the selected
   verifier; the refusal text names that sidecar. `docs/distribution/version-endpoint-contract.md` gains the
   two URLs, the namespace, the identity and the `ssh-keygen` command.
8. **Trust.** Every candidate is a binary the user's account can already run. A malicious binary that passes
   its known answer and lies later is outside the V1 threat model (accidental leaks only) and is no worse
   than a malicious `openssl` on PATH today. The pinned keys stay the only trust anchor.
9. **The refusal.** Exit 69, stderr lines:
   `cannot verify Ed25519 signatures: no usable openssl or ssh-keygen was found. Nothing was downloaded or installed.`,
   one `tried:` line per candidate, then the fix:
   `macOS: /usr/bin/ssh-keygen ships with macOS; restore it, or brew install openssl@3`,
   `Linux: OpenSSL 3.0 or newer is required (RHEL 8: dnf install openssl3 from EPEL; Ubuntu 20.04 / Debian 10: a newer distro or brew install openssl@3)`,
   `or name one: DECOY_OPENSSL=/path/to/openssl sh install.sh`. No "INVALID" and no "tampering".
10. **Exit codes.** 69 (`EX_UNAVAILABLE`) only for "cannot verify". Other refusals stay 1. 4 was rejected:
    it is the CLI's `EXIT_FINDINGS` (`src/decoy/cli/exit_codes.py:74`).
11. **Test gate.** `needs_shell_tools` becomes "an Ed25519-capable openssl or a usable `ssh-keygen`", checked
    with the same known answers from Python. A test of one route gates on that route's helper.

## 13. Pre-mortem

- P1. A custom Homebrew prefix: on a Mac the SSHSIG route installs anyway; on Linux the user sees exit 69 and
  `DECOY_OPENSSL`.
- P2. LibreSSL 3.7 or newer may pass Ed25519 but not `-rawin`: the known answer decides at run time.
- P3. OpenSSL 3.5 makes `-rawin` implied for EdDSA and still accepts the flag; the known answer catches a
  future change.
- P4. A future `ssh-keygen` changes `-Y verify` output or exit codes: only exit 0 passes, and the SSHSIG
  known answer runs on every install.
- P5. S0 forgets the `.sshsig` for one target: candidate completeness refuses it, and AT-M2 fails on a Mac
  for the macOS bundle.
- P6. The two key forms drift after a key rotation: `inject-keys` derives both from the one private key, and
  `check-keys` runs in S0 and in candidate completeness.
- P7. A shell test host with neither verifier skips with a named reason; AT-M1 cannot skip, it reports a
  precondition error.
- P8. A wrapper reads the installer exit as a CLI exit. 69 is outside the CLI's 0 to 6 and 130
  (`src/decoy/cli/exit_codes.py:74`).

## 1. FRAME

### Problem

Row 91 asks for three things. None exists today in a form that can ship.

1. **Download page.** `src/cli.njk:349-375` on decoy-web has a launch-only install section that tells users to
   "unpack it onto your path" and lists "Python 3.10 to 3.12". The signed bundle carries its own runtime and
   installs through `install.sh` or `install.ps1`, so the copy is wrong. All three buttons (Linux x86-64, macOS,
   Windows) link to `{{ site.github }}/releases/latest`; Linux aarch64 is missing; nothing shows a checksum, the
   release public key or its fingerprint. `site.json` still says "CLI BUSL-1.1".
2. **Update-check endpoint.** The CLI already has the client (`src/decoy/_update_check.py`) and two other
   fetchers of the same host (`src/decoy/cli/upgrade.py:46,57`, `src/decoy/distribution/installer.py:231`), plus
   `install.sh:25,38` and `install.ps1:34`. Every one but `installer.py` (which takes its URL from the caller) defaults to `https://decoy.dev/cli/...`, and so do
   `docs/install.md:18`, `packaging_tools/README.md:84` and the endpoint contract
   `docs/distribution/version-endpoint-contract.md:15-24`. Nothing is served
   there by any repo we own, and the vault still lists the domain as undecided (`v1-open-todos.md:42`). The site
   and mail domain is `trydecoy.com` (`src/CNAME`, `site.json`).
3. **`/proof` synced (B-3).** No `/proof` route exists on the current site. The proof components sit unused in
   `docs-src/components/marketing/proof/`, and the vendored `docs-src/lib/data/proof-manifest.json` is engine
   0.2.0 with 12 strategies against the engine's 0.26.0 with 14.

Four facts change the shape of the work:

- **The client leaks a version.** `_fetch_latest` builds `urllib.request.Request(url, headers={})` with the
  comment "no identifying headers", but urllib adds `User-Agent: Python-urllib/3.x`, so every check names the
  Python minor version. The docstring also claims "a config setting" opts out; no such setting exists (only the
  flag and `DECOY_NO_UPDATE_CHECK`). The body is read without a size cap, and `latest` is cached unvalidated.
- **Bundles cannot live on GitHub Pages.** decoy-web deploys to GitHub Pages (`.github/workflows/deploy.yml`).
  Pages caps a published site at 1 GB, has a soft 100 GB per month bandwidth limit, and its terms say it is not a
  free host for running an online business. One installed bundle is about 600 to 650 MB (packaging spec), so even
  compressed, four targets of one release fill the site. GitHub Release assets have a 2 GiB per-file cap and no
  bandwidth or total-size limit.
- **The signed document expires.** `version_document.DEFAULT_VALIDITY_DAYS` is 30 and `install.sh:252-263`
  refuses an expired document. Releases are monthly (owner 2026-11-12), so a late release breaks every new
  install unless the document is re-signed on a schedule.
- **GitHub Pages ignores `_headers` and `_redirects`.** Both files in `src/` use Cloudflare or Netlify syntax.
  Nothing in them takes effect today, and Pages cannot serve server-side redirects, so the installer's
  pinned-version convention `<base>/<ver>/decoy-<ver>-<target>.tar.gz` (`install.sh:309`, `installer.py:500`, and `upgrade.py:166`, which derives the base from the document URL)
  cannot be pointed at release assets by a redirect rule.

### Guarantee (what REL-WEB promises)

- G-1 A user on any supported target can install from `https://<host>/cli/` with one copied command, and the
  page lists exactly the targets the signed version document lists, with their SHA-256 and the key fingerprint.
- G-2 The update check is the privacy contract in 5.2, stated as assertions P1 to P8, each with a test.
- G-3 The endpoint is static files on the website's host; no server code of ours sees a request, so nothing is
  logged beyond what the host logs by default.
- G-4 The published version document is always signature-valid, unexpired by at least 10 days at deploy, and
  never lower in `serial` than the one it replaces.
- G-5 `/proof` renders the proof manifest of the D-4 engine tag, and its source digest is recorded for readiness
  row 12.

## 2. Established solutions

- **Static version manifest plus signed metadata.** TUF's timestamp role (signed, short expiry, monotonic version)
  is what `version_document.py` already follows. TUF keeps the timestamp fresh with a scheduled re-sign, which is
  what Q4 (a) adopts.
- **Install script served from the vendor domain, binaries from release storage.** `rustup`, `uv` and `deno` serve
  `install.sh` from their own domain and fetch binaries from GitHub Releases or object storage. `uv` publishes
  release assets on GitHub and its installer resolves them by tag. This is Q2 (a).
- **Update checks without identifiers.** Homebrew documents its analytics separately from its update fetch;
  `npm`'s update-notifier sends a plain registry GET. The pattern is a plain GET of a public file with a fixed or
  absent User-Agent, cached for a day, off in CI. The CLI client already follows it except for the UA.
- **Static-site build checks.** The site already fails its build on bad claims and links (`npm run check`). The
  new checks join that command rather than a new pipeline.

## 3. Design notes

1. **One host for the small files, release assets for the bundles (Q2 (a)).** Pages serves `version.json`, its
   `.sig`, `install.sh`, `install.ps1` and `release-key.pub` under `/cli/`. Bundles, their `.sig` and `.sha256`
   are assets on the `v<ver>` GitHub release of `louiskeep/decoy`. The signed document's `artifacts[target].url`
   is already absolute, so the latest path needs no client change.
2. **Pinned versions need a bundle base.** For a non-latest version both installers build
   `<base>/<ver>/<name>` from the document URL (`install.sh:309`, `installer.py:500`, and `upgrade.py:166`, which
   computes that base and passes it to `installer.install_version`). Under Q2 (a) RW-C2 adds one constant, the bundle base
   `https://github.com/louiskeep/decoy/releases/download`, and the convention becomes
   `<bundle_base>/v<ver>/decoy-<ver>-<target>.tar.gz`, overridable with `DECOY_BUNDLE_BASE`. The Ed25519
   signature against the pinned key stays the trust anchor (`install.sh:296-309` comment); the change moves
   bytes, not trust. `upgrade.py` passes the bundle base instead of the document base. Under Q2 (b) or (c) the
   convention stays and RW-C2 drops this part.
3. **The document lives in decoy-web git.** Row 94's publish step opens a decoy-web PR that adds
   `src/cli/version.json`, `.sig`, both install scripts and the public key. Git history is the publish log, a new
   `pull_request` workflow runs the verifier before merge (decoy-web has only `deploy.yml` today, on push to main and
   `workflow_dispatch`), and a merge deploys. Opening that PR from the CLI repo needs a cross-repo credential (Q8). No build step fetches anything from the network.
4. **The download page reads the signed document.** An Eleventy data file parses `src/cli/version.json` at build,
   and `cli.njk` renders one row per entry in `artifacts`. A platform appears only when its bundle is in the
   signed document; Windows appears when WIN-FEAS (row 89) lets row 94 publish it, with no page edit.
5. **`/proof` reuses the docs app.** `docs-src/lib/proof.ts` already validates the manifest with a zod schema and
   throws on a mismatch, and seven proof components exist. Q5 (a) mounts them as a page in the docs app, and
   `build-docs.sh` copies its export to `dist/proof/index.html`. The sync script records the engine tag and digest beside the vendored
   manifest.
6. **One resolver for the host.** The default host is a literal in `_update_check.py:36`, `upgrade.py:46`,
   `install.sh:38`, `install.ps1:34`, `docs/install.md:18`, `packaging_tools/README.md:84` and the endpoint contract.
   The two Python callers also disagree on the override: the notice honors `DECOY_VERSION_URL`, `decoy upgrade`
   (`upgrade.py:107`) does not. RW-C2 adds `version_document.resolve_version_url(override: str | None)` (the
   `--url` value, else `DECOY_VERSION_URL`, else `DEFAULT_URL`), used by both. The scripts and docs keep a literal,
   and a sentry asserts every literal equals `DEFAULT_URL` (AT-C7).

## 4. Release sequence (release-and-rollback)

Row 91 builds the place; row 94 publishes into it. The order inside row 94's publish, which this plan fixes:

1. Upload bundles, `.sig` and `.sha256` to the `v1.0.0` release (Q2 (a)) and confirm each URL returns 200.
2. Open the decoy-web PR with the signed `version.json`, `.sig`, scripts and key (Q8 credential). The PR workflow
   runs `npm run check`, which runs `check-dist.mjs` (5.1). Merge; `deploy.yml` reruns the check and Pages deploys.
3. Wait until `https://<host>/cli/version.json` serves the new `serial` (Pages caches for about 10 minutes), then
   run row 94's smoke from the published artifact.
4. Flip `prelaunch` to `false` in `site.json` in a separate decoy-web commit after the smoke is green.

Rollback: never `git revert` `src/cli/version.json`. Publish a new document with a higher `serial` whose `latest`
is the previous version and whose `artifacts` name that version's release assets (packaging spec, rollback). Row 94
S0's workflow gets a `rollback --latest <version>` mode that builds and signs that document and opens the same
decoy-web PR; nothing else can produce it, because only the workflow holds the key. `check-dist.mjs` refuses a lower serial, so a revert fails
the build (AT-H4). The download page then follows the document. A bad page edit alone is a normal revert.

Re-sign: under Q4 (a), row 94 S0's workflow gets a `resign` mode that bumps `serial` and `expires` with the same
`latest`, and opens the same decoy-web PR, every 14 days. With 30-day validity a document still has 16 days left
when it is replaced, so the scheduled warning at 10 days fires only when a re-sign was missed, and the deploy check
(expired or under 3 days) never blocks a routine page fix.

### 5.2 Update-check privacy contract (slices RW-C1 and RW-C2, CLI)

Each assertion is a test. "The request" is the one HTTP request `_fetch_latest` makes.

| Id | Assertion | Verified by |
|---|---|---|
| P1 | The request is `GET <path>` with no query string, no body, and exactly these headers: `Host`, `User-Agent: decoy-update-check`, `Accept-Encoding: identity`, `Connection: close`. No `Cookie`, `Authorization`, `Referer`, CLI version, Python version, OS or machine name. | AT-C1: a loopback `http.server` records the raw request line and headers; the test compares the set exactly. |
| P2 | No redirect is followed. Any 3xx ends the check with no notice. | AT-C2: the loopback server answers 302 to a second loopback port; the second port records zero requests. |
| P3 | At most one request per 24 hours per user cache. No request under CI, a non-TTY stdout or stderr, `--json`, `--no-update-check`, `DECOY_NO_UPDATE_CHECK`, an unresolved placeholder key, or a `_NO_NOTICE_COMMANDS` command. | AT-C3 (parametrized, a request counter on the loopback server); existing `tests/unit/test_distribution_acceptance.py:468-508` keep the key cases. |
| P4 | The cache file holds exactly `{"checked_at": int, "latest": str or null}`. No identifier is created or read anywhere in the check. | AT-C4 reads the cache keys; sentry AT-C8 (AST) fails on an import of `uuid` or `getpass`, or an attribute use of `getnode`, `gethostname`, `node` on `platform`, `getlogin`, `getuser` or `uname`, in `_update_check.py` and the `decoy.distribution` modules it imports (`version_document`, `layout`). `platform.machine` in `targets.py` stays legal. |
| P5 | The body is read with a 64 KiB cap. `latest` is cached and shown only when it parses as a `packaging` `Version`, and the notice prints `str(Version(latest))`, never the raw string. Any failure (network, 3xx, oversize, parse, bad version) writes `{"checked_at": now, "latest": null}`, so a bad response costs one request per 24 hours, as P3 requires. | AT-C5: a 1 MiB body, a 302, and a `latest` holding `\x1b[2J`; each leaves exactly `{"checked_at": <now>, "latest": null}` and prints nothing, and a second start inside 24 hours sends no request. |
| P6 | The endpoint is a static file on the website's host. No code of ours runs per request; logs are the host's defaults (for GitHub Pages, GitHub's own access logs, which the owner cannot read or extend). | AT-H3 (only static files in `dist/cli/`); AT-H6 (`deploy.yml` publishes `dist/` through `actions/deploy-pages` and nothing else); the download page states what the host sees (AT-D3). |
| P7 | The download page loads no third-party script and sets no cookie. | AT-H3 rule 7; AT-D4 runs the built page in a headless browser and records zero off-site requests and zero cookies. |
| P8 | Bundle downloads (`install.sh`, `decoy upgrade`) go to the bundle host, which sees the IP and the downloader's own User-Agent. Under Q2 (a) that is `github.com`, which redirects (302) to `release-assets.githubusercontent.com`; the page names both. Nothing of ours adds an identifier to those requests. | AT-D3 (copy); AT-C6 (the pinned URL is built from version and target only). |

## 1. FRAME

### 1.1 Facts at the base

1. **No release workflow.** `.github/workflows/` holds `ci.yml`, `regen-diagrams.yml` and
   `release-smoke.yml`. `release-smoke.yml` smokes the wheel only; its header says the gate
   "counts only the canonical smoke of the signed bundles".
2. **The build tools exist and run by hand.** `PT:build_bundle.py:242` (`--version`, `--target`,
   `--python`, `--wheels`, `--out`, `--sign`), `PT:make_version_document.py:61` (`--serial`
   defaults to the current time, `:66`; `--valid-days`, `:68`), `PT:sign_release.py:277`
   (`keygen`, `sign`, `pubkeys`, `inject-keys`, `check-keys` `:299`, `sshsig` `:302`).
   `PT:README.md` "Build pipeline" lists the manual steps, ending with "Publish ... to the
   download host".
3. **Candidate listing misses the new sidecars.** `PT:candidate.py:54` `listed()` takes
   `.tar.gz`, `.sig`, the two installers and `version.json`. A `.sshsig` or `.sha256` is not in
   `SHA256SUMS`, so a candidate with one removed still passes (PRE-S0 item 3 and 4).
4. **One write scope is allowed.** `ci/install-policy.toml:47` registers `regen-diagrams.yml`
   `contents`; `CT:sentry/test_ci_lock_installs.py:314` pins the allowlist at 1. Uploading release
   assets needs `contents: write` on one job. REL-IMAGE OQ-5 asks for 3 for its own jobs.
5. **The engine already has the pattern.** Engine `.github/workflows/native-companion-release.yml`
   (header lines 1 to 36): an ancestor-of-main preflight, the signing key's public half must equal
   the committed public key and must not be the placeholder, signing runs in the `native-release`
   Environment, the release is created as a draft and un-drafted only after every asset uploaded,
   and the shell logic sits in `scripts/release/native_release_checks.sh` so a sentry test can
   dry-run it (Actions does not run on this box).
6. **Bundles need three hosts.** `C:distribution/targets.py` lists `linux-x86_64`,
   `linux-aarch64`, `macos-arm64` (Windows gated). Each bundle embeds a standalone CPython and the
   target's native companion wheel, which come from the engine's signed native release
   (`PT:README.md` "Build pipeline" step 1).
7. **Owner answers in force (2026-11-15).** Download host `trydecoy.com` (REL-WEB Q1); bundles as
   GitHub Release assets (Q2); weekly re-sign when fewer than 17 days remain, 30-day validity (Q4);
   a GitHub App installed on decoy-web only, its key in the `native-release` Environment (Q8);
   SSH signatures in S0 (Mac Q1). Owner setup due 2026-12-01: release key and Environment, tag
   protection, qemu action SHA pin, DNS.

### 1.2 Pinned guarantee

1. A signed release set exists only if: the tagged commit is on `main`'s first-parent history; the
   signing key's public half equals `C:distribution/release_key.pub.pem` and that file is not the
   placeholder; every bundle, `version.json` and `install.sh` carries its `.sig`, `.sshsig` and
   `.sha256` as PRE-S0 lists; `install.sh` passes `check-keys`; and `candidate.py` accepts the set.
   Any one missing fails the workflow before anything leaves the runner.
2. `publish` makes the set public in REL-WEB section 4 order and never in a partial state: the
   GitHub Release stays a draft until every asset URL returns 200, the decoy-web PR is opened only
   after that, and `prelaunch` stays true until the published-artifact smoke is green.
3. `rollback --latest X` and `resign` only ever write a version document with a higher `serial`
   than the one live; they never edit or revert a published file.
4. The private key never leaves the signing job: no other job, artifact, log line or PR body holds
   it or a value derived from it other than signatures and the public fingerprint.

## 3. Design notes

1. **One workflow, four jobs.** `.github/workflows/release.yml`, triggered by a `v*` tag (build
   and sign) and by `workflow_dispatch` with a `mode` input (`publish`, `resign`, `rollback`).
   Tag run jobs: `preflight` (read-only), `build` (matrix over the three targets, read-only, no
   secret), `sign` (Environment `native-release`, read-only scope, holds the release key).
   Dispatch runs (`publish`, `resign`, `rollback`) have two jobs: `sign-doc` (Environment
   `native-release`, read-only, holds the key, reads the live document and signs a new one, design
   note 9) and then `publish` (Environment `native-release`, the one job with `contents: write`,
   mints the App token, never holds the release key). Top-level `permissions: contents: read`;
   workflow-level `concurrency: release` with no cancel, so no two release runs interleave.
2. **Build stages, sign finishes.** `build_bundle.py` signs `MANIFEST.json` inside the archive
   only when it holds the key (`PT:build_bundle.py:218`), and build jobs must not hold it. So
   `build_bundle.py` is split, behavior unchanged for the existing `--sign` path: `assemble_stage`
   (interpreter, wheels, launcher, unsigned `MANIFEST.json`) and `finish_bundle(stage,
   private_key)` (writes `MANIFEST.sig`, then the existing deterministic archive and its `.sig`
   and `.sha256`). A build job runs `assemble_stage` and packs the stage with the same
   deterministic archiver into `stage-<target>.tar` (upload-artifact drops file modes, a tar keeps
   them). The `sign` job extracts each stage with a safe extractor (no absolute path, no `..`, no
   link leaving the stage), recomputes the manifest with `manifest.compute_manifest` and requires
   it to equal the shipped unsigned `MANIFEST.json` byte for byte, then calls `finish_bundle`.
3. **One entry point, cohesive modules; one module owns the network.**
   `scripts/release/release_pipeline.py` is argument parsing and dispatch only (about 120 lines),
   subcommands `preflight`, `fetch-inputs`, `stage`, `sign-set`, `sign-doc`, `publish`,
   `open-web-pr`, `check-published`. The work sits in `scripts/release/_rel_inputs.py`
   (preflight, inputs and closure, staging; about 260), `_rel_signset.py` (finish, sidecars,
   candidate; about 200), `_rel_version.py` (live read, serial policy, document signing; about
   150), `_rel_publish.py` (draft, download-back, un-draft, public check, delete, web PR; about
   220) and `_rel_net.py` (about 100). Each stays under the module-size cap and gets a
   module-size sentry baseline only if one is required. Every network call (GitHub API through the `gh` CLI with the
   job's token, HTTPS GET of public URLs) goes through `scripts/release/_rel_net.py`, which
   tests replace with a fake. The workflow only calls the script. A sentry (AT-W1) walks
   `release.yml` and fails on `openssl`, `sign_release`, `gh`, `curl`, `wget` or `ssh-keygen` in a
   step that is not a `release_pipeline.py` call, and walks `scripts/release/` for `subprocess` or
   `urllib` imports outside `_rel_net.py` and the signing calls in `release_pipeline.py`.
4. **Signing is one pass over a fixed list.** In `sign-set`, after `finish_bundle` for each
   target: `make_version_document.py` writes `version.json` with `--base-url
   https://github.com/<owner>/<repo>/releases/download/vX.Y.Z` (Q2 (a)), `--min-supported` from
   `PT:release_inputs.toml`, `--valid-days 30` and `--serial` from design note 9; `inject-keys`
   builds `install.sh` and `check-keys` must pass; then every primary file (each tarball,
   `version.json`, `install.sh`, `install.ps1`) gets `.sig` (`sign_release.py sign`), `.sshsig`
   (`sign_release.py sshsig`) and `.sha256`; then `candidate.py write`. The suffix list is one
   constant in `PT:candidate.py` (`SIDECARS = (".sig", ".sshsig", ".sha256")`) read by both
   `listed()` and `sign-set`. `install.ps1` is published with its sidecars but no Windows bundle
   exists this cycle (Windows gated, `PT:candidate.py:39`).
5. **Candidate completeness.** `PT:candidate.py` refuses a set where any primary file lacks one of
   `SIDECARS`, or any sidecar is missing from `SHA256SUMS`, or `install.sh` fails `check-keys`,
   with `candidate_sidecar_missing` and `candidate_installer_key`. This is PRE-S0 item 4; RG-S's
   candidate mode reads the same function, so the local and published smokes agree.
6. **Preflight.** The tag's commit must be on `origin/main`'s first-parent chain (`git rev-list
   --first-parent origin/main` contains it; plain ancestry is not enough, since a commit merged
   from a side branch is an ancestor but was never main's head); `C:distribution/release_key.pub.pem`
   is not the placeholder; the tag equals `C:__version__`; the engine pin equals the engine tag in
   the candidate record. In `sign`, the only job with the key, the key's public half must equal the
   committed public key.
7. **Inputs are pinned in one registry.** New `PT:release_inputs.toml`: `min_supported`, the
   python-build-standalone release tag, the CPython version, and per target the asset file name and
   its SHA-256. `fetch-inputs` downloads each interpreter archive, checks the SHA-256 before
   extracting, and checks the extracted `bin/python3 --version` equals the pinned version where the
   host can run it (the aarch64 leg runs it under qemu). Native companion wheels come from the
   engine GitHub Release for the pinned engine version: `fetch-inputs` verifies that release's
   `SHA256SUMS.sig` with the committed release public key, then each wheel against
   `SHA256SUMS`, and takes exactly one wheel whose full tag equals `cp<XY>-cp<XY>-<platform
   tag>`, with `<XY>` from the pinned CPython version in `release_inputs.toml` and the platform tag
   from `C:distribution/targets.py`; the engine release ships cp310, cp311 and cp312 wheels per
   target, so zero or more than one match is a refusal (`native_wheel_unmatched`). A missing
   or bad `.sig` stops the build. The engine workflow signs `SHA256SUMS` with the same key (engine
   `native-companion-release.yml` header items 2 and 5).
   The rest of the wheel closure, per leg: the CLI wheel is built from the tagged checkout with the
   pinned `build==1.2.2` (as `ci.yml` does); the engine wheel is built the same way from the
   engine commit the lock pins (`requirements-dev.lock:380`, an immutable commit SHA); every
   third-party wheel comes from a new hash-locked runtime lock `PT:runtime.lock` (runtime
   dependencies only, written by `scripts/dev/lock.sh` beside the dev lock, every line with
   `--hash`), fetched with `pip download --require-hashes --only-binary=:all: --platform <target
   tag> --python-version <pinned>`. `stage` then runs `build_bundle`'s offline install
   (`--no-index`, `PT:build_bundle.py:88`), so nothing outside these inputs can enter.
   Key custody has one boundary: `scripts/release/_rel_key.py` with a `release_key()` context
   manager that reads `DECOY_RELEASE_KEY_PEM` into a 0600 temp file, yields the loaded key, and
   removes the file in a `finally`. `sign-set` and `sign-doc`, the only two key-bearing
   subcommands, use it; nothing else reads the variable (AT-W1). Release codes have one registry:
   `PT:release_codes.py`, a closed `enum.Enum` of every code `candidate.py` and the `_rel_*`
   modules emit (the exit-path list in section 9 is a copy for readers; AT-W3 guards it). A new lock
   file is a full-suite trigger for S0a1.
8. **Publish order (REL-WEB section 4), with GitHub draft behavior.** Draft assets are not on
   the public URL, so the check is in two steps. `publish run_id=N`: (a) download the signed set
   from the `sign` run `N` and re-run the candidate check on it; (b) create the draft release
   `vX.Y.Z` (or reuse a draft with that tag) and upload every asset; (c) download every asset back
   through the authenticated API and require its SHA-256 to match `SHA256SUMS`; (d) un-draft; (e)
   GET every public asset URL and require status 200 and the same SHA-256; (f) `open-web-pr`: the
   signed `version.json`, its sidecars, the signed installers and the public key, through a per-run
   App token. The App token is minted and the decoy-web branch pushed before (d), so the steps
   after un-draft are only the public check and the PR call. Any failure after (d) and before the
   PR exists (public check, live re-read, PR call) deletes the release and the pushed web branch
   and fails; nothing links to the release until the PR merges. A public release with the same tag and other digests
   is a hard failure. The decoy-web merge, the serial wait, the smoke and the `prelaunch` flip are
   operator steps (section 4).
9. **Serials: every published document is signed just before it is published.** The tag run's
   `version.json` is for the candidate and the local smoke only; it is never sent to decoy-web.
   Each dispatch run's `sign-doc` job reads the live `https://trydecoy.com/cli/version.json`; if
   it exists its signature must verify with the committed public key, and the new `serial` is
   `max(live + 1, now)`; if the site serves none (before launch, HTTP 404 only), `serial = now`.
   Any other HTTP error stops. It signs the new document (`.sig`, `.sshsig`, `.sha256`) and hands
   it to `publish` as a job artifact. `publish` (for `publish` mode, after step (e)) and
   `open-web-pr` re-read the live serial right before opening the PR and refuse if it is not
   lower than the signed one (a re-run then signs again). Two open PRs that merge out of order
   are refused by decoy-web's `check-dist.mjs` serial rule (REL-WEB AT-H4). `publish` mode builds
   the document from the candidate's `latest` and artifact digests; `resign` (weekly cron, acts
   under 17 days left) keeps the live `latest` and artifacts; `rollback --latest X` points them at
   release `vX`, whose public assets must pass step (e) first. Neither mode changes GitHub Release
   assets.
10. **No secret in outputs.** The key is read from `DECOY_RELEASE_KEY_PEM` into a 0600 temp file
    inside `sign-set` and removed in a `finally`; every error path prints a fixed code only (no
    exception text, no file content); the PR body is a fixed template with the version, serial and
    the public fingerprint.

Rollback: before R7 nothing links to the release, so delete the draft or leave the public Release
unlinked and fix forward. After R7, a broken release is rolled back with `rollback --latest X` to

`prelaunch: true` again on decoy-web (a normal revert of that commit) while a 1.0.1 is built.
Published GitHub Release assets are never edited in place; a bad asset means a new version.

## 5. Behavior

- `release.yml` on tag: preflight, build x3, sign. Output: one workflow artifact `release-set`
  holding the signed set plus `candidate.json`. No public side effect.
- `release.yml` dispatch `publish run_id=N`: design note 8 (a) to (f). Idempotent on re-run: an
  existing draft with the same tag is reused; an existing public release with different asset
  digests is a hard failure.
- `release.yml` dispatch `resign` (also weekly cron): no-op exit 0 with "no re-sign needed" when 17
  or more days remain; otherwise a decoy-web PR.
- `release.yml` dispatch `rollback latest=X`: refuses when release `vX` public assets fail design
  note 8 step (e).
- S1 smoke: `smoke_install.py --from-published URL --candidate candidate.json --pubkey PEM
  --target T` downloads the published bundles, installers and sidecars into a temp dir and
  refuses unless each digest equals its line in the candidate's `SHA256SUMS` (whose own digest
  must equal `candidate.json`); the live `version.json` is not in the candidate (it was signed
  later, design note 9), so S1 verifies its signature with `--pubkey` and requires its artifact
  digests to equal the candidate's bundle lines. Then it runs the RG-S candidate steps against it and additionally installs
  through the published `install.sh` URL. Writes the same summary schema
  (`decoy-release-smoke/v1`) with `source: published`.

  runner. Recommended: GitHub-hosted `macos-14` for macOS and qemu (the SHA pin already on the
  owner list) for aarch64, both run once per release. Alternative: the Mac mini as a self-hosted
  runner for macOS (no hosted minutes, but a self-hosted runner in the signing workflow's build
  leg widens the trust boundary).

  `prelaunch: true` on decoy-web while 1.0.1 is built. Accept? Recommended: yes.

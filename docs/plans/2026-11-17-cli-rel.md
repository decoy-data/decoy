### 1.2 Pinned guarantee

1. A signed release set exists only if: the run's repository is exactly `decoy-data/decoy`; the
   run is on a `v*` tag whose commit is on `main`'s first-parent history; the version chain
   (design note 14) holds at every link; the signing key's public half equals
   `C:distribution/release_key.pub.pem` and that file is not the placeholder; the bundled
   companion is the pinned `native-v*` release fetched from exactly `decoy-data/decoy-engine` and
   every kernel's ABI matches the engine commit; every bundle, `version.json` and `install.sh`
   carries `.sig`, `.sshsig` and `.sha256`; every artifact URL in `version.json` is exactly
   `<ARTIFACT_BASE>/v<version>/<name>`; `install.sh` passes `check-keys`; and `candidate.py`
   accepts the set. Any one missing fails the workflow before the key is loaded or before
   anything leaves the runner.
2. A key-bearing job signs only over a set from a successful `release.yml` push run in exactly
   `decoy-data/decoy` (run repository and head repository) on the tag `v<version>`, where
   `version` is the required publish dispatch input, the run's `head_branch` is exactly that tag,
   the candidate's `cli_version` is exactly `version`, the head SHA is the tag's peeled commit,
   and every signature verifies with the committed key. It runs only on `refs/heads/main`
   (dispatch) or the tag (push).
3. `publish` never links a partial set: the host holds exactly the candidate asset-name set under
   `v<version>/` before any check passes; nothing links to it until the decoy-web PR merges; the
   PR is opened only after every object read back from the host origin and every public URL
   returns the candidate's bytes; and the published-artifact smoke runs before that PR merges.
4. `publish`, `rollback --latest X` and `resign` only ever write a document with a higher
   `serial` than the one live (field rules unchanged from revision 6, design note 11). They never
   edit or delete a published object.
5. The decoy-web commit the publish path makes has author and committer exactly
   `ckeep <decoy@trydecoy.com>`, set at one choke point and read back before push.
6. The private key and the job token that writes the release never leave the steps that use them: no other
   job, artifact, log line or PR body holds them or a value derived from them other than
   signatures and the public fingerprint.

## 2. Established solutions

Search run: GitHub "Using environments for deployment" (deployment branch and tag policies,
required reviewers), "Automatic token authentication" (least-privilege `permissions`, `actions:
read` for cross-run artifact download), `actions/create-github-app-token` (`owner`,
`repositories`, `permission-*` inputs), the draft-release flow of `goreleaser` and `cargo-dist`,
TUF timestamp metadata (monotonic version, expiry, re-sign), SLSA build provenance (verify which
workflow run and which source repository produced an artifact before trusting it), `uv pip
compile --universal`/`--python-platform`, the engine's own `native-companion-release.yml` and its
`check-version`, and the release layout of static download hosts (Python's
`python.org/ftp/python/<ver>/`, Node's `nodejs.org/dist/v<ver>/`, Rust's `static.rust-lang.org`):
immutable per-version paths, a long-lived immutable cache policy on versioned objects, and a small
short-lived index file that is the only thing a release changes.

- Build jobs hold no secret; one job holds the key; one job publishes (cargo-dist, engine).
- A signer checks the producing run's identity (workflow path, event, ref, head SHA, source
  repository, conclusion) before it signs, as SLSA verifiers check provenance.
- Deployment policies restrict which refs may enter the Environment that holds the key.
- Monotonic `serial`, expiry and periodic re-sign follow TUF timestamp metadata.
- Per-target hashed locks with `--no-build` refuse sdist-only dependencies.
- Versioned paths are never overwritten; the index (`version.json`) flips visibility.

Custom code left: the glue script, the run-identity check, the version chain, the centralized
candidate verifier, the host adapter interface and the web commit choke point. No new dependency
in this plan; the GitHub adapter uses the REST releases API through the existing `gh`.

## 3. Design notes

1. **One workflow, two run shapes.** `.github/workflows/release.yml`, triggered by a `v*` tag
   push (jobs `preflight`, `build` matrix x3, `sign`) and by `workflow_dispatch` with `mode`
   (`publish`, `resign`, `rollback`), required `version` for publish, and `run_id` plus `latest`
   where the selected mode needs them. Dispatch inputs reach Python only through fixed job-level
   environment names, including `DECOY_RELEASE_VERSION`; YAML never interpolates an input into
   shell source or an argv token. A weekly `schedule` selects `resign` (jobs `sign-doc`, then
   `publish`). Top-level `permissions: contents: read`. Per job: `build` contents read; `sign`
   contents read; `sign-doc` contents read and `actions: read`; `publish` contents write and
   `actions: read` (the one repository write: it creates the draft GitHub release that hosts the
   bundles, the OQ-1 exact-identity entry). `sign`, `sign-doc` and `publish` use Environment
   `native-release`. `concurrency: release`, no cancel. The release key secret is set only on the
   step that signs in each of `sign` and `sign-doc`; the job token reaches `gh` only on the
   `publish` step (as `GH_TOKEN`); neither at workflow or job scope. The App token step pins `owner: decoy-data`,
   `repositories: decoy-web`, `permission-contents: write`, `permission-pull-requests: write`.
2. **Ref and repository guard in every job.** The first step of every job is
   `release_pipeline.py guard-ref`, which refuses unless `GITHUB_REPOSITORY` equals
   `release_identity.CLI_REPO` exactly and `GITHUB_REF` is `refs/heads/main` (dispatch and
   `schedule`) or, for the tag-run jobs, `refs/tags/v<version>` on main's first-parent chain. R0
   sets the `native-release` Environment deployment policy separately in each repository: CLI
   allows `main` and `v*`; engine allows `main` and `native-v*`. The same key sits in both.
3. **Build stages, sign finishes.** Unchanged from revision 6: `build_bundle.py` splits into
   `assemble_stage` (interpreter, wheels, launcher, `BUNDLE_INFO.json`, unsigned
   `MANIFEST.json`) and `finish_bundle(stage, private_key)`; a build job packs
   `stage-<target>.tar`; `sign` extracts safely, recomputes the manifest, requires byte equality,
   then finishes. This catches accidental corruption between jobs only.
4. **One entry point; named owners for network, subprocess, host and git.**
   `scripts/release/release_pipeline.py` is argument parsing and dispatch only (about 130 lines,
   no signing call): `preflight`, `guard-ref`, `check-version`, `fetch-inputs`, `stage`,
   `sign-set`, `check-run`, `sign-doc`, `publish`, `cleanup`, `check-published`. Work modules:
   `_rel_inputs.py` (inputs, closure, staging; about 260), `_rel_signset.py` (finish, sidecars,
   candidate; about 200), `_rel_run.py` (run identity, design note 10; about 130),
   `_rel_chain.py` (version chain, design note 14; about 120), `_rel_version.py` (live read,
   serial, document build and signing; about 170), `_rel_publish.py` (host publish order, resume,
   public check, cleanup; about 200), `_rel_host.py` (the host adapter interface, the fake used
   by tests, and the GitHub release adapter added by S0h; about 150 before S0h), `_rel_web.py` (decoy-web
   branch, commit and PR, design note 15; about 120), `_rel_net.py` (HTTP GET and the GitHub API
   through `gh`; about 100), `_rel_key.py` (about 50). `_rel_inputs.py` keeps the one
   `_run_tool(argv, stage_python=...)` policy boundary of revision 6 (resolved executable
   identity; fixed shapes `sys.executable -m pip download|install`, `sys.executable -m build`,
   bundled interpreter `--version`, bundled interpreter `-I -m decoy.distribution.selfcheck
   --json`, bundled interpreter `-I -m decoy --version`, and the fixed `git` fetch and checkout
   subcommands). `_rel_web.py` has its own fixed git shapes (`clone` of exactly
   `release_identity.WEB_REPO`, `checkout -b`, `add`, `commit`, `log -1 --format`, `push`); no other
   module runs `git commit` or `git push` (AT-W1).
5. **Signing is one pass over a fixed list.** In `sign-set`: `finish_bundle` per target;
   `version.json` from `build_document` with each artifact entry built by one function,
   `release_identity.artifact_url(version, name)`, which returns
   `f"{ARTIFACT_BASE}/v{version}/{name}"`; `min_supported` from `PT:release_inputs.toml`, 30-day
   validity, `serial` per design note 11; `inject-keys` then `check-keys`; every primary file
   (each tarball, `version.json`, `install.sh`, `install.ps1`) gets `.sig`, `.sshsig` and
   `.sha256`; then `candidate.py write`. The suffix list is one constant, `PT:candidate.py`
   `SIDECARS = (".sig", ".sshsig", ".sha256")`; an AST sentry finds the literal once.
6. **One release-set verifier.** Unchanged from revision 6: `PT:candidate.py`
   `verify_release_set(dist, public_key)` is the only verifier used by `sign-set`, `check-run`,
   `publish` and both RG-S smoke modes; it now also requires every `version.json` artifact URL to
   equal `release_identity.artifact_url(...)` exactly (`candidate_artifact_origin`). It returns the
   immutable asset-name set (`{candidate.json, SHA256SUMS}` plus every name in `SHA256SUMS`) that
   publish, resume and public checks compare against.
7. **Inputs pinned in the existing registries.** Unchanged from revision 6 (interpreters as
   `[[binary_tool]]` entries fetched by `fetch_ci_binary.py` with a whole-archive mode; the

8. **One key boundary over the existing loader.** Unchanged: `_rel_key.release_key()` calls

9. **Release codes have one registry.** `PT:release_codes.py`, a closed `enum.Enum` of every code

10. **Run identity before any key use over an artifact.** `check-run N` (`_rel_run.py`, called

    value, so no installer default changes) and `ARTIFACT_HOST_EXCEPTION = "owner 2026-11-18: V1
    bundles are GitHub Release assets of decoy-data/decoy, a dated exception to the 2026-11-12
    static site plus CDN decision"`. The rule stays: a GitHub origin (`github.com`,
    `*.githubusercontent.com`) is refused by `release_identity` validation and by
    `verify_release_set` unless `ARTIFACT_HOST_EXCEPTION` names a dated owner decision, so removing
    the exception without moving the host fails closed. Tests inject a fixture origin. The host is
    reached only through `_rel_host.HostAdapter`, five operations: `list(version) -> {name:
    sha256}` (authenticated listing that sees a draft); `put_new(version, name, path)`
    (create-only: refuses if the name exists); `read_origin(version, name) -> bytes`
    (authenticated download, works on a draft); `public_url(version, name)` (= `artifact_url`);
    and `seal(version)` (makes every object public at once). The adapter has no delete operation
    and `_rel_net` has no `DELETE` call shape (AT-W1). S0b builds the interface, the publish order
    and a fake host (local directory origin plus a 127.0.0.1 public layer that serves 404 for every
    name until `seal` and can then serve stale bytes). S0h adds the GitHub release adapter:
    `list` and `read_origin` read the release for tag `v<version>` through the REST API, draft
    included; `put_new` creates the draft release on the existing tag if absent and uploads one
    asset, and GitHub refuses a second asset of the same name (`already_exists`), which the
    adapter maps to `publish_release_conflict`; `seal` sets `draft: false`, so every asset
    becomes public in one step; a release already published is never edited.
13. **Publish order, cache, resume and rollback on the host.** `publish version=V run_id=N`:
    (a) `guard-ref`; `check-run N` binds the run and candidate to V and to `CLI_REPO`.
    (b) Plan: `list(V)`. Every listed name must be in the candidate asset-name set with the
    candidate digest; an extra name or a same name with another digest is
    `publish_release_conflict` and stops (never overwrite, never delete). (c) Upload: `put_new`
    every candidate asset not yet listed (into the draft); then `list(V)` must equal the candidate
    asset-name set exactly, and `read_origin` of every asset must hash to the candidate
    `SHA256SUMS` line. (d) `seal(V)`: only after (c) passes; all assets become public together. (e)
    Public: GET every `public_url` (redirects followed only to `release-assets.githubusercontent.com`
    or `objects.githubusercontent.com`); require 200 and the candidate SHA-256. A 404 or 5xx is
    retried at most 6 times 20 seconds apart, then `publish_asset_unavailable`; a 200 with other
    bytes stops at once with `publish_digest_mismatch`. No public URL is requested before the
    seal, so no cache can hold a pre-upload 404. (f) Mint
    the App token; `_rel_web` pushes the decoy-web branch and opens the PR (signed `version.json`
    from `sign-doc`, sidecars, installers, public key). Visibility is atomic at the document:
    versioned objects are unreferenced until the PR merges and Pages serves the new serial (R6),
    so a partial upload is never linked. Freshness: `version.json` is the only mutable file and
    lives on the website; R6 waits until the live serial equals the signed one; the weekly resign
    keeps `expires` ahead. Resume: a re-run with the same V and N repeats (a) to (f); (b) and (c)
    skip names already present with equal digests; a release already sealed with the exact set
    skips to (e), and a sealed release with any other set is `publish_release_conflict`. The final `publish` step with `if: failure()
    || cancelled()` runs `cleanup`, which deletes a pushed decoy-web branch with no merged PR and
    records `publish_incomplete`; it never deletes a host object. Rollback: published version
    prefixes are kept forever (no lifecycle rule; R0 checks), so `rollback --latest X` only signs a
    new document pointing at `vX`'s objects after (c) and (e) pass on them. A version with wrong
    bytes is never fixed or deleted: it goes in `yanked` and the fix ships as the next patch
    version.
14. **The version chain, refused before key use.** `_rel_chain.check_version(expected, *,
    tree, wheels=None, stages=None, candidate=None)` is the one owner, modelled on the engine's
    `check-version` (fact 8): one call per phase, every link compared with `==` on the exact
    string after `packaging.version.Version` validation, each link a separate refusal detail.

Rollback: before R6 nothing links to the objects; close the PR and fix forward. After R6, a
broken release is rolled back with `rollback --latest X` (higher serial, bad version yanked), or,
for 1.0.0, by reverting the `prelaunch: false` commit (owner OQ-3) while 1.0.1 is built.
Published objects are never edited; a bad object means a new patch version.

Runbook notes (`docs/release/runbook.md`): approvals per dispatch; `concurrency` behaviour; an
unlinked version prefix (cleanup ran, no PR merged) is resumed by re-running `publish` with the
same `version` and `run_id`, or, if its bytes are wrong, yanked and replaced by the next patch
(never deleted); a hard runner loss leaves the draft unsealed and unlinked and the operator re-runs
`cleanup` before resuming; the host checklist (draft release on the existing tag, no asset
deletion, names never repeat).

## 5. Behavior

- Tag run: preflight (repository, ref, version chain links 1 to 3), build x3 (stage, links 4 to
  6), sign (links 1 to 5 and 7, then key). Output: workflow artifact `release-set` (signed set
  plus `candidate.json`). No public side effect.
- `publish version=V run_id=N`: design note 13. `resign`: no-op exit 0 when 17 or more days
  remain; otherwise a decoy-web PR. `rollback latest=X`: refuses when `vX`'s objects fail (c) or
  (e) or its tag-run document does not verify.
- Every decoy-web commit made by these modes: `ckeep <decoy@trydecoy.com>` as author and
  committer, or no push.
- S1: `smoke_install.py --from-published --candidate candidate.json --pubkey PEM --target T
  [--version-doc FILE]`, code in `PT:smoke/_published.py`. Downloads the bundles, installers and
  sidecars once from `artifact_url(V, name)` into a temp dir; each digest must equal its line in
  the candidate's `SHA256SUMS` (whose digest must equal `candidate.json`); the given
  `version.json` must verify with `--pubkey`, its artifact digests must equal the candidate's
  bundle lines, and its artifact URLs must equal `artifact_url(V, name)`. Then the RG-S candidate
  steps, then two installs with the published `install.sh` (`PT:install/install.sh:251-265` keeps
  the routes exclusive): (i) offline, `DECOY_LOCAL_BUNDLE` on the checked tarball; (ii) online,
  `DECOY_VERSION_URL` on the harness's local server; the installer downloads the bundle from the
  URL the document names, which is the host. The harness records requests; (ii) passes only when
  the document and its `.sig` were fetched from it. Summary `decoy-release-smoke/v1` with
  `source: published`.

### 1.2 Pinned guarantee

1. A signed release set exists only if: the run is on a `v*` tag whose commit is on `main`'s
   first-parent history; the signing key's public half equals
   `C:distribution/release_key.pub.pem` and that file is not the placeholder; the bundled
   companion is the pinned `native-v*` release and every kernel's ABI matches the engine commit;
   every bundle, `version.json` and `install.sh` carries `.sig`, `.sshsig` and `.sha256`;
   `install.sh` passes `check-keys`; and `candidate.py` accepts the set. Any one missing fails the
   workflow before anything leaves the runner.
2. A key-bearing job signs only over a set from a successful `release.yml` push run on the tag
   `vX.Y.Z` of this repository, whose head SHA is the tag commit, and whose every signature
   verifies with the committed key; it runs only on `refs/heads/main` (dispatch) or the tag (push).
3. `publish` never leaves a set linked while partial: nothing links to a release until the
   decoy-web PR merges, the PR is opened only after every public asset returns the candidate's
   bytes, and the published-artifact smoke runs before that PR merges.
4. `rollback --latest X` and `resign` only ever write a document with a higher `serial` than the
   one live, carrying every field of the live document except `serial` and `expires` (rollback
   also adds the bad version to `yanked`); they never edit a published file.
5. The private key never leaves the key-bearing jobs: no other job, artifact, log line or PR
   body holds it or a value derived from it other than signatures and the public fingerprint.

## 3. Design notes

1. **One workflow, two run shapes.** `.github/workflows/release.yml`, triggered by a `v*` tag
   push (jobs `preflight`, `build` matrix x3, `sign`) and by `workflow_dispatch` with `mode`
   (`publish`, `resign`, `rollback`) plus a weekly `schedule` for `resign` (jobs `sign-doc`, then
   `publish`). Top-level `permissions: contents: read`. Per job: `build` contents read; `sign`
   contents read; `sign-doc` contents read and `actions: read` (it downloads run `N`'s artifact);
   `publish` `contents: write` and `actions: read`. `sign`, `sign-doc` and `publish` use
   Environment `native-release`. `concurrency: release`, no cancel. The App token step pins
   `repositories: decoy-web`, `permission-contents: write`, `permission-pull-requests: write`.
2. **Ref guard in every dispatch job.** The first step of `sign-doc` and of `publish` is
   `release_pipeline.py guard-ref`, which refuses unless `GITHUB_REF` is `refs/heads/main`
   (`schedule` runs use the default branch, which is `main`); the tag-run `preflight` refuses
   unless `GITHUB_REF` is `refs/tags/v*` on main's first-parent chain. R0 sets the
   `native-release` Environment's deployment policy to "selected branches and tags": `main` and
   `v*`, in both the CLI and the engine repos (the same key sits in both).
3. **Build stages, sign finishes.** `build_bundle.py` is split, behaviour unchanged for the
   existing `--sign` path: `assemble_stage` (interpreter, wheels, launcher, unsigned
   `MANIFEST.json`) and `finish_bundle(stage, private_key)` (`MANIFEST.sig`, then the existing
   deterministic archive with `.sig` and `.sha256`). A build job packs the stage into
   `stage-<target>.tar`. The `sign` job extracts with a safe extractor (no absolute path, no `..`,
   no link leaving the stage), recomputes the manifest with `manifest.compute_manifest`, requires
   byte equality with the shipped `MANIFEST.json`, then calls `finish_bundle`. This catches
   accidental corruption between jobs; the build jobs are inside the same trust boundary
   (same workflow, no secret, pinned inputs), so it is not a defence against a hostile build job.
4. **One entry point; named owners for network and subprocess.**
   `scripts/release/release_pipeline.py` is argument parsing and dispatch only (about 120 lines,
   no signing call): `preflight`, `guard-ref`, `fetch-inputs`, `stage`, `sign-set`, `check-run`,
   `sign-doc`, `publish`, `cleanup`, `check-published`. Work modules: `_rel_inputs.py` (inputs,
   closure, staging; about 260), `_rel_signset.py` (finish, sidecars, candidate; about 200),
   `_rel_run.py` (run identity and set verification, design note 10; about 120),
   `_rel_version.py` (live read, serial, document build and signing; about 170), `_rel_publish.py`
   (draft, download-back, un-draft, public check, web PR, cleanup; about 220), `_rel_net.py` (HTTP
   GET and the GitHub API through `gh`; about 100), `_rel_key.py` (about 50). Subprocess calls
   that are not network-to-GitHub are named, not hidden: `_rel_inputs.py` runs `pip download`,
   `git` (engine checkout at the locked commit) and `python -m build`, and only through one helper
   `_run_tool(argv)` whose first element must be in a closed set (`pip`, `git`, `python`); the
   sentry (AT-W1) checks that set. Interpreters are fetched by `scripts/dev/fetch_ci_binary.py`
   (design note 7), not by `_rel_net`.
5. **Signing is one pass over a fixed list.** In `sign-set`: `finish_bundle` per target;
   `version.json` from `build_document` with base URL
   `https://github.com/<owner>/<repo>/releases/download/vX.Y.Z`, `min_supported` from
   `PT:release_inputs.toml`, 30-day validity, `serial` per design note 11; `inject-keys` then
   `check-keys`; every primary file (each tarball, `version.json`, `install.sh`, `install.ps1`)
   gets `.sig`, `.sshsig` and `.sha256`; then `candidate.py write`. The suffix list is one
   constant, `PT:candidate.py` `SIDECARS = (".sig", ".sshsig", ".sha256")`, read by `listed()` and
   `sign-set`; an AST sentry finds the literal tuple once in the tree.
6. **Candidate completeness.** `PT:candidate.py` refuses a set where any primary file lacks one of
   `SIDECARS`, a sidecar is missing from `SHA256SUMS`, or `install.sh` fails `check-keys`
   (`candidate_sidecar_missing`, `candidate_installer_key`). RG-S's candidate mode reads the same
   function.
7. **Inputs pinned in the existing registries.**
   - Interpreters: one `[[binary_tool]]` entry per target in `ci/install-policy.toml`
     (`python-<target>`, url, version, sha256 from the upstream checksums), fetched by
     `fetch_ci_binary.py`, which gains a whole-archive mode (`--extract-to DIR` for an entry with
     `member = "python/"`); its digest-before-extract rule is unchanged. The extracted
     `bin/python3 --version` must equal the pinned version (aarch64 under qemu).
   - Native companion: `PT:release_inputs.toml` pins `native_tag` (for example `native-v0.1.0`),
     `native_version` and `min_supported`. `fetch-inputs` reads the engine release at
     `native_tag`, verifies its `SHA256SUMS.sig` with the committed release public key, checks
     each wheel against `SHA256SUMS`, and takes exactly one wheel whose full tag equals
     `cp<XY>-cp<XY>-<platform tag>` and whose version equals `native_version`; zero or more than
     one is `native_wheel_unmatched`. `build_bundle._install_wheels` installs
     `decoy-engine-native==<native_version>`. After the offline install, `stage` runs the bundled
     interpreter on `decoy_engine.execution.native` companion status and requires every kernel
     loaded with a matching ABI tag (`native_abi_mismatch` otherwise): this is the check that the
     engine commit accepts this companion, since the engine pins no version.
   - Third-party wheels: three per-target locks `PT:locks/runtime-<target>.lock`, written by
     `scripts/dev/lock.sh` with `uv pip compile --no-build --generate-hashes --python-version
     <pinned> --python-platform <x86_64-unknown-linux-gnu | aarch64-unknown-linux-gnu |
     aarch64-apple-darwin>` over the runtime dependencies only, and checked by `lock.sh --check`.
     `fetch-inputs` runs `pip download --require-hashes --only-binary=:all: --no-deps -r
     <target lock> --python-version <pinned>` with the full platform tag list for the target
     (`manylinux_2_17` through `manylinux_2_28` plus `manylinux2014` for Linux,
     `macosx_11_0_arm64` through `macosx_14_0_arm64` for macOS), so an sdist-only dependency fails
     at lock time.
   - CLI and engine wheels: built with `python -m build --no-isolation` inside a venv installed
     from a hashed `PT:locks/build.lock` (`build==1.2.2`, `hatchling` and its closure, hashed,
     `--no-build`); the engine source is the commit `requirements-dev.lock` pins.
   - `stage` installs offline (`--no-index`, `PT:build_bundle.py:88`).
8. **One key boundary over the existing loader.** `scripts/release/_rel_key.py`
   `release_key()` calls `sign_release.load_private_key()` (no second reader, no temp file of its
   own), then requires that the public half equals the committed public key and that the
   committed key is not the placeholder (`sign_key_mismatch`, `preflight_placeholder_key`), and
   yields the key. `sign-set` and `sign-doc` both get the checks by using it. `ssh-keygen` signing
   keeps going through `sign_release.sshsig_file`, the existing owner of its 0600 temp file.
9. **Release codes have one registry.** `PT:release_codes.py`, a closed `enum.Enum` of every
   code `candidate.py`, the `_rel_*` modules and `PT:smoke/` emit (including
   `smoke_candidate_mismatch` and `smoke_download_failed`). AT-W3 guards it; section 9's list is a
   reader copy.
10. **Run identity before any key use over an artifact.** `check-run N` (in `_rel_run.py`, called
    first by `sign-doc` for `publish` mode and again by `publish` step (a)) reads run `N` through
    the API and requires: `path == ".github/workflows/release.yml"`, `event == "push"`,
    `head_branch == "vX.Y.Z"`, `head_sha` equal to the commit the tag `vX.Y.Z` resolves to now,
    `conclusion == "success"`, and `head_repository` equal to this repository. It then downloads
    the `release-set` artifact of run `N` only, and verifies every `.sig` and each archive's
    in-archive `MANIFEST.sig` with the committed public key (`run_identity_mismatch`,
    `run_signature_invalid`). A fork-PR artifact, an old tag's run, a failed run or a set signed
    by another key is refused before the key is loaded.
11. **Serials and documents.** The tag run's `version.json` serves the candidate and the local
    smoke only. Each dispatch run's `sign-doc` reads the live `https://trydecoy.com/cli/version.json`;
    if present its signature must verify with the committed key; new `serial = max(live + 1,
    now)`; a 404 before launch gives `now`; any other error stops. Documents are built with
    `version_document.build_document`, not `make_version_document.py`: `publish` mode takes
    `latest` and artifact entries from the verified candidate and `min_supported` from
    `release_inputs.toml`; `resign` copies `latest`, `min_supported`, `artifacts`, `yanked` and
    `message` from the live document; `rollback --latest X` takes `artifacts` from release `vX`'s
    signed tag-run `version.json` (verified with the committed key, public assets passing step (e)),
    copies `min_supported` and `message`, and adds the current `latest` to `yanked`. `publish`
    re-reads the live serial right before opening the PR and refuses if it is not lower than the
    signed one. Out-of-order merges are refused by decoy-web's `check-dist.mjs` serial rule.
12. **Publish order, with resume.** `publish run_id=N`: (a) `check-run N` and the candidate
    check; (b) create the draft `vX.Y.Z` (or reuse a draft with that tag) and upload every asset;
    (c) download every asset back through the authenticated API and require its SHA-256 to match
    the candidate `SHA256SUMS`; (d) un-draft; (e) GET every public URL, require 200 and the same
    SHA-256; (f) mint the App token, push the decoy-web branch and open the PR (signed
    `version.json` from `sign-doc`, sidecars, installers, public key). A re-run with the same `N`
    that finds a public release with the candidate's digests resumes at (e); a public release with
    other digests is `publish_release_conflict` and stops. A final step `if: failure() ||
    cancelled()` runs `release_pipeline.py cleanup`, which deletes a pushed decoy-web branch with
    no merged PR and records `publish_incomplete`; it never deletes a public release (a re-run
    resumes it, and nothing links to it until the PR merges). The repository's immutable-releases
    setting is OFF (R0 checks it) so a draft can be replaced; a release whose public bytes are
    wrong is never fixed in place: it is deleted by hand per the runbook and the fix ships as the
    next patch version.
13. **No secret in outputs.** Every error path prints a fixed code only; the PR body is a fixed
    template with version, serial and public fingerprint.

Rollback: before R6 nothing links to the release; close the PR and fix forward. After R6, a

Runbook notes (`docs/release/runbook.md`): the weekly `resign` cron waits for an approver each
week, and each dispatch asks for two approvals; with `concurrency` and no cancel, a newer pending
run replaces an older pending one, so a second dispatch while one waits cancels the waiting one;
an orphaned public release (cleanup ran, no PR merged) is either resumed by re-running `publish`
with the same `run_id` or, if its bytes are wrong, deleted by hand and replaced by the next patch.

## 5. Behavior

- Tag run: preflight, build x3, sign. Output: workflow artifact `release-set` (signed set plus
  `candidate.json`). No public side effect.
- `publish run_id=N`: design note 12. `resign`: no-op exit 0 when 17 or more days remain;
  otherwise a decoy-web PR. `rollback latest=X`: refuses when `vX`'s public assets fail step (e)
  or its tag-run document does not verify.
- S1: `smoke_install.py --from-published URL --candidate candidate.json --pubkey PEM --target T
  [--version-doc FILE]`, code in `PT:smoke/_published.py`. Downloads the published bundles,
  installers and sidecars once into a temp dir; each digest must equal its line in the candidate's
  `SHA256SUMS` (whose digest must equal `candidate.json`); the given `version.json` must verify
  with `--pubkey` and its artifact digests must equal the candidate's bundle lines. Then the RG-S
  candidate steps, then an install through the published `install.sh` with `DECOY_VERSION_URL`
  pointing at the harness's local copy of that document. Summary `decoy-release-smoke/v1` with
  `source: published`.

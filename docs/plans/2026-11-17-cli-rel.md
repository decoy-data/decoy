## 1. FRAME

### 1.1 Facts at the base

1. **No release workflow.** `.github/workflows/` holds `ci.yml`, `regen-diagrams.yml` and
   `release-smoke.yml`. `release-smoke.yml` smokes the wheel only; its header says the gate
   "counts only the canonical smoke of the signed bundles".
2. **The build tools exist and run by hand.** `PT:build_bundle.py:242` (`--version`, `--target`,
   `--python`, `--wheels`, `--out`, `--sign`), `PT:make_version_document.py:61` (`--serial`
   defaults to the current time, `:66`; `--valid-days`, `:68`), `PT:sign_release.py:277`
   (`keygen`, `sign`, `pubkeys`, `inject-keys`, `check-keys` `:299`, `sshsig` `:302`).
   `PT:README.md` "Build pipeline" lists the manual steps, ending with "Publish ... to the
   download host".
3. **Candidate listing misses the new sidecars.** `PT:candidate.py:54` `listed()` takes
   `.tar.gz`, `.sig`, the two installers and `version.json`. A `.sshsig` or `.sha256` is not in
   `SHA256SUMS`, so a candidate with one removed still passes (PRE-S0 item 3 and 4).
4. **One write scope is allowed.** `ci/install-policy.toml:47` registers `regen-diagrams.yml`
   `contents`; `CT:sentry/test_ci_lock_installs.py:314` pins the allowlist at 1. Uploading release
   assets needs `contents: write` on one job. REL-IMAGE OQ-5 asks for 3 for its own jobs.
5. **The engine already has the pattern.** Engine `.github/workflows/native-companion-release.yml`
   (header lines 1 to 36): an ancestor-of-main preflight, the signing key's public half must equal
   the committed public key and must not be the placeholder, signing runs in the `native-release`
   Environment, the release is created as a draft and un-drafted only after every asset uploaded,
   and the shell logic sits in `scripts/release/native_release_checks.sh` so a sentry test can
   dry-run it (Actions does not run on this box).
6. **Bundles need three hosts.** `C:distribution/targets.py` lists `linux-x86_64`,
   `linux-aarch64`, `macos-arm64` (Windows gated). Each bundle embeds a standalone CPython and the
   target's native companion wheel, which come from the engine's signed native release
   (`PT:README.md` "Build pipeline" step 1).
7. **Owner answers in force (2026-11-15).** Download host `trydecoy.com` (REL-WEB Q1); bundles as
   GitHub Release assets (Q2); weekly re-sign when fewer than 17 days remain, 30-day validity (Q4);
   a GitHub App installed on decoy-web only, its key in the `native-release` Environment (Q8);
   SSH signatures in S0 (Mac Q1). Owner setup due 2026-12-01: release key and Environment, tag
   protection, qemu action SHA pin, DNS.

### 1.2 Pinned guarantee

1. A signed release set exists only if: the tagged commit is on `main`'s first-parent history; the
   signing key's public half equals `C:distribution/release_key.pub.pem` and that file is not the
   placeholder; every bundle, `version.json` and `install.sh` carries its `.sig`, `.sshsig` and
   `.sha256` as PRE-S0 lists; `install.sh` passes `check-keys`; and `candidate.py` accepts the set.
   Any one missing fails the workflow before anything leaves the runner.
2. `publish` makes the set public in REL-WEB section 4 order and never in a partial state: the
   GitHub Release stays a draft until every asset URL returns 200, the decoy-web PR is opened only
   after that, and `prelaunch` stays true until the published-artifact smoke is green.
3. `rollback --latest X` and `resign` only ever write a version document with a higher `serial`
   than the one live; they never edit or revert a published file.
4. The private key never leaves the signing job: no other job, artifact, log line or PR body holds
   it or a value derived from it other than signatures and the public fingerprint.

## 3. Design notes

1. **One workflow, four jobs.** `.github/workflows/release.yml`, triggered by a `v*` tag (build
   and sign) and by `workflow_dispatch` with a `mode` input (`publish`, `resign`, `rollback`).
   Jobs: `preflight` (read-only), `build` (matrix over the three targets, read-only, no secret,
   unsigned bundles uploaded as 14-day workflow artifacts), `sign` (Environment `native-release`,
   read-only scope, holds the key, writes the signed set and `candidate.json` as a workflow
   artifact), `publish` (Environment `native-release`, the one job with `contents: write`, also
   mints the App token). Top-level `permissions: contents: read`.
2. **Logic in one script, dry-runnable.** `scripts/release/release_pipeline.py` with subcommands
   `preflight`, `sign-set`, `publish-plan`, `version-doc` and `check-published`. The workflow only
   calls it. Each subcommand takes paths and environment, never reaches the network except
   `check-published` (HTTP HEAD on the listed URLs), and is tested with a throwaway key on the
   devbox-free test hosts. This is the choke point: no signing or upload command is written inline
   in YAML, and a sentry walks `release.yml` for `openssl`, `sign_release`, `gh release` and
   `curl` outside a `release_pipeline.py` call.
3. **Signing is one pass over a fixed list.** `sign-set` takes the unsigned bundles and runs, for
   each tarball and for `version.json`: `sign_release.py sign` (`.sig`), `sign_release.py sshsig`
   (`.sshsig`), and writes `.sha256`. It then runs `inject-keys` on `install.sh` and `check-keys`
   on the result, signs `install.sh` the same way, and calls `candidate.py write`. The list of
   sidecar suffixes is one constant in `PT:candidate.py` (`SIDECARS = (".sig", ".sshsig",
   ".sha256")`) that both `listed()` and `sign-set` read.
4. **Candidate completeness.** `PT:candidate.py` refuses a set where any listed primary file
   (tarball, `version.json`, `install.sh`) lacks one of `SIDECARS`, or where `install.sh` fails
   `check-keys`, with the codes `candidate_sidecar_missing` and `candidate_installer_key`. This is
   PRE-S0 item 4, and RG-S's candidate mode reads the same function, so the local smoke and the
   published smoke agree.
5. **Preflight.** Mirrors the engine: the tag's commit is an ancestor of `origin/main` on
   first-parent history; `C:distribution/release_key.pub.pem` is not the placeholder; the
   Environment key's public half equals it (checked in `sign`, the only job holding the key); the
   tag equals `C:__version__`; the engine pin in `pyproject.toml` equals the engine tag in the
   candidate record.
6. **Inputs are pinned, not fetched loose.** Native companion wheels are downloaded from the engine
   GitHub Release named by the pinned engine version and checked against that release's signed
   `SHA256SUMS` with the same release public key before `build_bundle.py` runs. CPython comes from
   `uv python install` at the version pinned in `PT:` (as `PT:README.md` step 2). The aarch64
   build runs under the qemu action at the owner-approved SHA pin; macOS uses a GitHub-hosted
   `macos-14` runner (OQ-2).
7. **Publish order (REL-WEB section 4).** `publish`: (a) download the signed set from the `sign`
   run named by `run_id`, re-run `candidate.py` check on it; (b) create a draft GitHub Release
   `vX.Y.Z` and upload every asset; (c) `check-published` until every asset URL returns 200 and the
   downloaded bytes hash to `SHA256SUMS`, then un-draft; (d) open the decoy-web PR with the signed
   `version.json`, its sidecars, the signed installers and the public key, using a per-run App
   token; (e) stop. The decoy-web merge, the serial wait, the smoke and the `prelaunch` flip are
   operator steps in section 4, because each waits on a human or on decoy-web CI.
8. **`resign` and `rollback`.** `version-doc` reads the live document from
   `https://trydecoy.com/cli/version.json`, verifies its signature with the committed public key,
   and writes a new one with `serial = max(live serial + 1, now)`. `resign` keeps `latest` and the
   artifacts and runs only when fewer than 17 days remain (weekly cron); `rollback --latest X`
   points `latest` and `artifacts` at release `vX`, whose assets must already exist (checked with
   `check-published`). Both open the same decoy-web PR. Neither touches GitHub Release assets.
9. **No secret in outputs.** The key is read from `DECOY_RELEASE_KEY_PEM` into a 0600 temp file
   inside `sign-set` and removed in a `finally`; `release_pipeline.py` never prints environment
   values; the PR body is a fixed template with the version, serial and the public fingerprint.

`prelaunch: true` again on decoy-web (a normal revert of that commit) while a 1.0.1 is built.
Published GitHub Release assets are never edited in place; a bad asset means a new version.

## 5. Behavior

- `release.yml` on tag: preflight, build x3, sign. Output: one workflow artifact `release-set`
  holding the signed set plus `candidate.json`. No public side effect.
- `release.yml` dispatch `publish run_id=N`: design note 7 (a) to (d). Idempotent on re-run: an
  existing draft with the same tag is reused; an existing public release with different asset
  digests is a hard failure.
- `release.yml` dispatch `resign` (also weekly cron): no-op exit 0 with "no re-sign needed" when 17
  or more days remain; otherwise a decoy-web PR.
- `release.yml` dispatch `rollback latest=X`: refuses when release `vX` assets are not all 200.
- S1 smoke: `smoke_install.py --from-published URL --candidate candidate.json --pubkey PEM
  --target T` downloads the published set into a temp dir, refuses unless its `SHA256SUMS` digest
  equals `candidate.json`, then runs the RG-S candidate steps against it and additionally installs
  through the published `install.sh` URL. Writes the same summary schema
  (`decoy-release-smoke/v1`) with `source: published`.

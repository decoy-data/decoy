## 1. Goal, guarantee, non-goals

Goal: each CLI release also publishes one official container image for running Decoy pipelines in
CI and on Kubernetes, built from the same signed Linux bundle the download ships.

The guarantee this plan makes, and the whole of what review holds it to:

1. **Same bytes.** The managed runtime inside the image (`/opt/decoy`) is the signed Linux bundle
   for that release and architecture, laid down by the shipped installer's offline path
   (`install.sh` with `DECOY_LOCAL_BUNDLE`), so every file in the slot verifies against the bundle's
   signed manifest. The image adds only an OS base, `tini`, a non-root user and one marker file.
2. **Two architectures, one reference.** Each published tag is an OCI index with `linux/amd64` and
   `linux/arm64`. Every published index digest is signed, and is recorded in the release's signed
   version document, so a user can pin and verify it with or without network access to a public
   transparency log.
3. **Non-root.** The image runs as UID 10001 by default, runs under any other non-root UID with a
   read-only root filesystem, and contains no setuid file.
4. **License refusal.** Inside the image, every `decoy` command except `decoy --version` and
   `decoy --help` refuses with exit 1 and code `image.license_not_accepted` until the license is accepted
   (section 5.5). The refusal reads no config, source or project file, writes nothing, and its
   text never contains the value the user set.
5. **Image mode.** Inside the image `decoy upgrade` refuses (`image.upgrade_unsupported`, exit 1)
   and the startup update check never runs. Outside the image (download bundle, pip, dev) nothing
   changes.
6. **Recipes that run.** The public docs carry a GitHub Actions, a GitLab CI and a Kubernetes Job
   recipe, and CI runs each recipe's commands against the built image.

Non-goals (a finding here is a follow-up item, not a blocker):

- A GitHub Action, Helm chart or Terraform module (owner 2026-11-07: after V1).
- Gating the Python library inside the image (`import decoy` through the bundled interpreter).
  The gate covers the `decoy` command, as the native runtime guard does today.
- Defeating a user who removes the marker or rebuilds the image. The threat model is honest and
  accidental use; the license is enforced by contract (license-enforcement-v1).
- Windows or macOS images, and an image tarball on the download host (V2-LOG, section 12).
- Bit-for-bit reproducible images. The bundle is reproducible; the OS layer is pinned by digest
  and package version only.

## 4. Design notes

- **One module owns image mode** (`src/decoy/distribution/image_gate.py`): it is the only reader
  of the marker, the only holder of the accepted license id and the only home of `image.*` codes.
  The root callback calls it once, before `runtime_guard`. Principle: one place per fact; the
  change pain it removes is a second check drifting from the first when the license id changes.
- **Image mode needs both facts**: the marker file exists AND `layout.managed_home()` is not
  None. A dev checkout with a stray `/etc/decoy/image.json` is not an image; a bundle install
  without the marker is not an image.
- **Fail closed on a bad marker.** An unreadable or malformed marker under a managed runtime still
  means image mode. A broken image must refuse, not run ungated.
- **No flag argument.** `enforce(invoked_subcommand)` returns a refusal or None, as
  `runtime_guard.enforce` does.
- **Environment reads stay in `_env_flags`.** A new `env_text(name)` reader returns the stripped
  value or None and never logs it; `image_gate` compares it. The existing environment-read sentry
  covers the new variable without a baseline change.
- **The image adds no Python.** Everything inside `/opt/decoy` comes from the bundle; `tini`,
  the user and the marker are the only additions.

## 5. Behavior

### 5.1 Build inputs

Per release and architecture: `decoy-<ver>-linux-<arch>.tar.gz` plus `.sig` and `.sha256`
produced by REL-PKG, and the release's `install.sh` with the public key already embedded (the
`__DECOY_RELEASE_PUBLIC_KEY__` placeholder filled at publish time). The release job uses the same
files it publishes to the download host, read from the release workflow's artifacts, not
re-downloaded.

`packaging_tools/image_context.py` stages a Docker build context: those four files, the
Dockerfile, the marker template filled with `variant` and `version`, and `LICENSE.md` and `NOTICE`
from the bundle. It refuses an `install.sh` that still carries the placeholder, so an image is
never built that trusts an unfilled key.

### 5.2 Image layout

Multi-stage `packaging_tools/image/Dockerfile`, both stages `FROM debian:bookworm-slim@sha256:<pinned>`
(glibc 2.36, above the bundle's manylinux_2_28 floor):

1. Stage `install`: install `openssl`, `ca-certificates` (pinned versions); run
   `DECOY_HOME=/opt/decoy DECOY_BIN_DIR=/opt/decoy/bin DECOY_LOCAL_BUNDLE=/ctx/<bundle> sh /ctx/install.sh --version <ver>`.
   The installer's own signature, checksum, manifest and native self-checks run here; any failure
   fails the build.
2. Stage `final`: install `tini` (pinned version); `COPY --from=install /opt/decoy /opt/decoy`
   owned by root, not writable by others; `/usr/local/bin/decoy` links to the launcher;
   `/etc/decoy/image.json` (root, mode 0444) holds
   `{"schema": "decoy-image/v1", "variant": "slim", "version": "<ver>"}`; `/opt/decoy/LICENSE.md`
   and `NOTICE`; user `decoy` with UID and GID 10001; `HOME=/home/decoy` with mode 1777, so any
   UID can write it; `WORKDIR /work`; `ENV DECOY_HOME=/opt/decoy`;
   `USER 10001:10001`; `ENTRYPOINT ["/usr/bin/tini", "--"]`; `CMD ["decoy", "--help"]`.
   OCI labels: `org.opencontainers.image.version`, `.revision`, `.source`, `.licenses`
   (`FSL-1.1-ALv2`), `.title`.

No package manager cache, no compiler, no setuid bits (the build strips any that the base ships,
and test T-I2 checks).

### 5.3 Tags and digests

Per release `X.Y.Z`: tags `X.Y.Z`, `X.Y`, `X`, `latest` for slim, and `X.Y.Z-ner`, `X.Y-ner`,
`X-ner`, `ner` for the NER variant (5.7). Full-version tags are never moved or deleted. Moving tags
move only after the new index is signed and tested. Docs and recipes always pin
`@sha256:<index digest>`; tags are for discovery.

The version document gains an optional top-level field (additive; the contract already says unknown
top-level fields are ignored, `version-endpoint-contract.md:71`):

```json
"images": {
  "slim": {"ref": "<registry>/<name>:1.0.0", "digest": "sha256:<index digest>"},
  "ner":  {"ref": "<registry>/<name>:1.0.0-ner", "digest": "sha256:<index digest>"}
}
```

`make_version_document` takes the digests as input; the release order becomes: bundles, images,
then the signed version document (section 5.10).

### 5.4 Signing and verification

- In the publish job: `cosign sign --recursive` on each index digest (keyless, GitHub OIDC,
  `id-token: write`), build provenance via `actions/attest-build-provenance`, and
  `cosign attest` with the bundle's release SBOM as an SPDX predicate.
- Online check (docs): `cosign verify <ref>@<digest> --certificate-oidc-issuer
  https://token.actions.githubusercontent.com --certificate-identity-regexp
  '^https://github.com/<owner>/decoy/.github/workflows/release-image.yml@refs/tags/v'`.
- Offline check (docs): verify `version.json` with the pinned release key exactly as the install
  docs show, then compare its `images.*.digest` with the digest of the mirrored image. This needs
  no new key and no transparency-log access.
- The publish job runs both checks against what it just pushed before it moves any tag.

### 5.5 License refusal

Working answer to OQ-1 (option a): the license is valid when `DECOY_ACCEPT_LICENSE`, stripped
and compared without case, equals `FSL-1.1-ALv2`. `ACCEPTED_LICENSE_ID` is a constant in
`image_gate.py`; a test ties it to the `## Abbreviation` line of the repo's `LICENSE.md`, so a
license change cannot leave the gate on the old id.

In image mode, the root callback refuses before any other work when the value is unset, empty or
anything else:

```text
error: [image.license_not_accepted] This Decoy container image runs only after you accept its
license. Read it at /opt/decoy/LICENSE.md, then set DECOY_ACCEPT_LICENSE=FSL-1.1-ALv2.
  hint: see the container guide: https://decoy.dev/docs/container
```

- Exit 1 (`EXIT_USAGE`): the fix is in the user's invocation. No new exit code.
- Written through `emit_error` in human mode to stderr; stdout stays empty. The root callback runs
  before a subcommand parses `--json`, so a `--json` caller gets exit 1 and empty stdout, the same
  as today's native runtime refusal (V2-LOG item: root refusals as a `decoy-error-v1` object).
- The text is fixed. It never contains the variable's value, a path from the environment, or
  anything read from the marker.
- `decoy --version` and `decoy --help` (and bare `decoy`) exit during the root group's own
  argument parsing, before the root callback, and so keep working. `decoy <command> --help` is
  parsed after the root callback (Click runs the group callback, then builds the subcommand's
  context), so it is refused like the command itself; the refusal text says how to accept. The
  image's default `CMD` is `decoy --help`, which works unaccepted.

Option (b), if the owner picks it in OQ-1, replaces only `image_gate._license_ok()` with an
offline Ed25519-signed license file check (`/run/secrets/decoy-license` or
`DECOY_LICENSE_FILE`), verified against a separate pinned license key with
`decoy.distribution.signing.verify_detached`, adding codes `image.license_invalid`. Everything
else in this plan stays. It also needs license issuing tooling, a second key with custody, and a
customer delivery flow, which this plan does not cover (section 13).

### 5.6 Other image-mode behavior

- `decoy upgrade` refuses with `image.upgrade_unsupported`, exit 1: "This command upgrades a
  downloaded install. In a container, pull a newer image instead." It runs no network call. The
  check sits in `image_gate.enforce`, so `upgrade.py` does not change.
- The startup update notice never runs in image mode (no network, no cache write under the
  read-only `/opt/decoy`).
- Order in the root callback: `image_gate.enforce`, then `runtime_guard.enforce`, then the update
  notice. The license refusal therefore wins over a native-companion refusal: an unaccepted image
  never reports internals.

### 5.7 The `-ner` variant

Built `FROM` the slim image's final stage. It installs spaCy and the model by running, at build
time, the same model-install command row 32a gives bundle users, in its offline mode, with the
spaCy closure and the model wheel pinned by hash (`NER_MODEL_WHEELS` for `DEFAULT_NER_MODEL`, today
`en_core_web_sm` 3.8.0, `md` if row 32c lands). The marker says `"variant": "ner"`.

The image has no NER install path of its own. Until row 32a's model-install command is merged, the
`-ner` tags are not published and the release ships slim only (OQ-4).

### 5.8 Runtime posture

- Default user 10001; any other non-root UID works because HOME is mode 1777 and nothing under
  `/opt/decoy` is written at run time.
- Read-only root filesystem works with a writable `/tmp` and HOME (tmpfs or `emptyDir`), plus the
  mounted work folder.
- Secrets reach the container only through the environment or mounted files the user supplies
  (`DECOY_MASK_SECRET` and cloud credentials as the CLI already reads them); the image holds none.

### 5.9 Public docs and recipes

`docs/guides/container/README.md` (synced to decoy.dev by REL-DOCS, row 92) covers: pull by digest,
accept the license, verify (online and offline), mount a project, pass `DECOY_MASK_SECRET`, exit
codes, and the three recipes, each a complete file beside the guide:

- `github-actions.yml`: one job, a `docker run --rm --user "$(id -u):$(id -g)"
  -v "$GITHUB_WORKSPACE:/work" -e DECOY_ACCEPT_LICENSE -e DECOY_MASK_SECRET <ref>@<digest> decoy run
  <pipeline>` step, with the secret from repository secrets.
- `gitlab-ci.yml`: `image: <ref>@<digest>`, variables from masked CI/CD variables, `script:
  decoy run <pipeline>`.
- `k8s-job.yaml`: a Job meeting Pod Security "restricted": `runAsNonRoot`, `runAsUser: 10001`,
  `readOnlyRootFilesystem`, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`,
  `seccompProfile: RuntimeDefault`, `emptyDir` on `/tmp` and `/home/decoy`, the project from a
  PersistentVolumeClaim, the license and mask secret from a Secret.

Recipes use the placeholder `<ref>@<digest>`; the release job writes the real digest into the
published docs page.

### 5.10 CI job placement

- **PR lane** `.github/workflows/image.yml`, on pull requests touching `packaging_tools/image/**`,
  `packaging_tools/image_context.py`, `src/decoy/distribution/**`, `src/decoy/__main__.py` or
  `docs/guides/container/**`, and on `workflow_dispatch`: build a dev-signed bundle with a throwaway
  key (the path `smoke_install` already uses), build the slim image for `linux/amd64`, run
  `tests/container/` against it. No push, no signing, no secrets. The lane is registered in
  `ci/required-jobs.toml` only after it has run green for a week (it is advisory first).
- **Release lane** `.github/workflows/release-image.yml`, called by REL-PKG's release workflow
  after bundles are built and signed. Jobs: `build` (matrix amd64 on `ubuntu-latest`, arm64 on
  `ubuntu-24.04-arm`; push by digest only), `test` (each arch on its native runner, the full
  `tests/container/` set against the pushed digest), `publish` (Environment `native-release`,
  required approver; creates the indexes, signs, attests, verifies, then moves tags last), then
  hands the digests to the version-document step.
- Every third-party action is pinned to a full commit SHA; cosign is pinned by version and
  checksum. Permissions per job, least first: `contents: read` by default, `packages: write`,
  `id-token: write` and `attestations: write` only in `publish`.
- Spend: GitHub-hosted runners and GHCR public packages are free for this public repository. No
  VM, no paid registry.

### 5.11 Release and rollback

An image is part of the release unit (bundles, images, version document). Preconditions: both
arches built from the signed bundles, every `tests/container/` test green on each arch, signatures
verified. Rollback: point the moving tags back to the previous index digest and publish the version
document that names it; never delete a published digest, since users pin them. Post-release signal:
the publish job's own pull-and-run of each moving tag before the release is announced.

## 6. Failure modes

| Failure | Behavior |
|---|---|
| Bundle signature, checksum or manifest fails in the build stage | `install.sh` refuses; build fails; nothing pushed |
| `install.sh` still has the key placeholder | `image_context.py` refuses before Docker runs |
| One arch fails to build or test | `publish` does not run; no index, no tag, no version-document change |
| Signing or attestation fails | Pushed digests stay untagged; the release stops before the version document |
| Post-push verify fails (wrong identity, digest mismatch) | Tags not moved; release stops |
| Marker missing in a built image | T-I1 fails in CI (the image would run ungated) |
| Marker unreadable or malformed at run time | Image mode still on; refusal unless accepted |
| User sets a wrong license value, possibly a secret by mistake | Same refusal; value never printed |
| User runs as root (`--user 0`) | Works; documented as unsupported; gate still applies |
| Read-only root without writable `/tmp` or HOME | Decoy's existing errors for an unwritable temp or project path; the guide names the two mounts |
| `decoy upgrade` in the image | `image.upgrade_unsupported`, exit 1, no network |
| Row 32a model install not merged at release | `-ner` not published; slim ships (OQ-4) |
| Registry outage during publish | Job fails; rerun publishes the same digests (push by digest is idempotent) |

## 8. Choke point, enumerations and class table

### 8.1 Choke point

The rule "every `decoy` command in an image is gated" is enforced by construction in the Typer
root callback, which runs before every subcommand. Guard: T-G10's AST check plus T-G1, which is
parametrized over the registered command list from `app`, so a new command is covered without
editing the test. Mutation: removing the call turns both red.

### 8.2 Exit paths of the gate and the build

The gate sits in the root callback at `src/decoy/__main__.py:252`, before the update notice at
`src/decoy/__main__.py:260`; `--version` exits in its eager callback at
`src/decoy/__main__.py:208`.

Run time (CLI, in image mode):

1. Not accepted: exit 1, `image.license_not_accepted`, nothing read or written (T-G1, T-G2, T-I4).
2. Accepted, `upgrade`: exit 1, `image.upgrade_unsupported`, no network (T-G7).
3. Accepted, native self-check fails: today's `runtime_guard` refusal, exit 3 (unchanged).
4. Accepted, any other command: the command's own exits, unchanged (T-G3, T-I3).
5. `decoy --version`, `decoy --help`, bare `decoy`: exit 0 before the gate (T-G6).
6. Marker unreadable or malformed: path 1 or 2 as for a good marker (T-G5).

Build and release (each stops the release with nothing published past that step):
`image_context.py` refusal; `install.sh` refusal in the build stage; a failed container test on
either arch; failed sign or attest; failed post-push verify. Section 6 lists each.

## 13. Owner questions (each with a recommended answer)

- **OQ-1. What counts as "a valid license" for the public image?** The CLI has no license-key
  system: FSL-1.1-ALv2 grants use for permitted purposes without a key, and the paid platform's
  key is deliberately not enforced (license-enforcement-v1). Options: (a) accept-license
  variable, `DECOY_ACCEPT_LICENSE=FSL-1.1-ALv2`, the established `ACCEPT_EULA` pattern; no key, no
  network, works air-gapped. (b) An offline Ed25519-signed license file per customer, verified
  against a pinned license key; needs issuing tooling, a second key with custody and a delivery
  flow, and matches a paid CLI tier that does not exist today. **Recommended: (a)**; (b) stays a
  V2-LOG item and swaps one function if chosen later.
- **OQ-2. Registry and image name.** Options: GHCR under a GitHub organization for the licensor
  (for example `ghcr.io/<org>/decoy`), GHCR under `louiskeep`, or Docker Hub (anonymous pull rate
  limits unless paid). The name is hard to change after launch because users pin it.
  **Recommended: GHCR under an organization** (owner creates it), public package, free for public
  images; `louiskeep` only if no organization is planned.
- **OQ-3. Signing method.** Options: cosign keyless with the GitHub OIDC identity (each signature
  is a public Rekor entry naming the repository and workflow; no key to hold), or cosign with a
  long-lived key held in `native-release`. **Recommended: keyless**, plus the digests in the
  Ed25519-signed version document for users who verify with the release key only.
- **OQ-4. `-ner` without row 32a.** If the model-install command is not merged by a release, ship
  slim only and add `-ner` in the first release after it lands. **Recommended: yes**, so the image
  never carries an NER install path of its own.

Owner tasks this plan needs before IMG-4 (no decision, just setup): create the organization or
choose the namespace (OQ-2), allow the `native-release` Environment to issue OIDC tokens to
`release-image.yml`, and make the package public after the first push.

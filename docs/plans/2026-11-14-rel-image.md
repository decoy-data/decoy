## 1. Goal, guarantee, non-goals

Goal: each CLI release also publishes one official container image for running Decoy pipelines in
CI and on Kubernetes, built from the same signed Linux bundle the download ships.

The guarantee this plan makes, and the whole of what review holds it to:

1. **Same bytes.** The managed runtime inside the image (`/opt/decoy`) is the signed Linux bundle
   for that release and architecture, laid down by the shipped installer's offline path
   (`install.sh` with `DECOY_LOCAL_BUNDLE`), and its slot passes `verify_extracted` against the
   pinned release key. The image adds only an OS base with `ca-certificates`, `tini`, a non-root
   user, one marker file, a PATH link and one license link (5.2). The `-ner` variant adds exactly
   what row 32a's model install adds for bundle users (5.7).
2. **Two architectures, one reference.** Each published tag is an OCI index with `linux/amd64` and
   `linux/arm64`. Every published index digest is signed, and is recorded in a per-release file
   signed with the existing Ed25519 release key, so a user can pin and verify it with or without
   access to a public transparency log, for the current release and every older one.
3. **Non-root.** The image runs as UID 10001 by default, runs under any other non-root UID with a
   read-only root filesystem, and contains no setuid or setgid file.
4. **License refusal.** Inside the image, every `decoy` invocation except the root group's own
   eager options (`decoy --version`, `decoy --help`, `--install-completion`, `--show-completion`)
   and bare `decoy` refuses with exit 1 and code `image.license_not_accepted` until the license is
   accepted (5.5). The refusal reads no config, source or project file, writes nothing, and its
   text never contains the value the user set.
5. **Image mode.** Inside the image `decoy upgrade` refuses (`image.upgrade_unsupported`, exit 1)
   and the startup update check never runs. Outside the image (download bundle, pip, dev) nothing
   changes, and the gate never raises.
6. **Recipes that run.** The public docs carry a GitHub Actions, a GitLab CI and a Kubernetes Job
   recipe. The image lane runs the GitHub Actions and GitLab commands against the built image and
   runs the Kubernetes Job on a kind cluster (5.10, T-R1 to T-R3).

Non-goals (a finding here is a follow-up item, not a blocker):

- A GitHub Action, Helm chart or Terraform module (owner 2026-11-07: after V1).
- Gating the Python library inside the image (`import decoy` through the bundled interpreter).
  The gate covers the `decoy` command, as the native runtime guard does today.
- Defeating a user who removes the marker or rebuilds the image. The threat model is honest and
  accidental use; the license is enforced by contract (license-enforcement-v1).
- Windows or macOS images, and an image tarball on the download host (V2-LOG, section 12).
- Bit-for-bit reproducible images. The bundle is reproducible; the OS layer is pinned by base
  digest only.

## 4. Design notes

- **One module owns image mode** (`src/decoy/distribution/image_gate.py`): it is the only reader
  of the marker, the only holder of the accepted license id and the only home of `image.*` codes.
  Principle: one place per fact; the change pain it removes is a second check drifting from the
  first when the license id changes.
- **`image_mode()` is computed once.** `image_gate.image_mode()` is cached for the process (one
  marker read). `enforce(invoked_subcommand)` and the root callback's notice suppression both call
  it, so the callback can suppress the notice after a license is accepted.
- **Image mode needs both facts, checked in this order**: `layout.managed_home()` is not None
  first, so pip and dev installs never touch `/etc`; then `os.lstat("/etc/decoy/image.json")`.
  Only `FileNotFoundError` means "absent". Any other `OSError` (EACCES, ELOOP, a dangling link
  reads as ENOENT through `stat` but not through `lstat`) means present and malformed.
- **Fail closed on a bad marker.** Malformed means image mode with variant unknown: the gate
  applies. The marker is read with a 4 KiB bound, `O_NOFOLLOW`, and must be a JSON object with
  exactly the keys `schema`, `variant`, `version`, each a string, `schema == "decoy-image/v1"`.
- **Never raise.** `image_gate` catches every `Exception` from its own reads and turns it into
  "malformed" (inside a managed runtime) or "not image" (outside one); nothing from it reaches the
  user as a traceback, and no exception text reaches any output.
- **One named environment reader.** `_env_flags.license_acceptance()` reads only
  `DECOY_ACCEPT_LICENSE` and returns the stripped value or None, never logged. There is no generic
  text reader, so the environment-read sentry still sees every variable name.
- **No flag argument.** `enforce(invoked_subcommand)` returns a refusal or None, as
  `runtime_guard.enforce` does.
- **The image adds no Python.** Everything inside `/opt/decoy` comes from the bundle (or, for
  `-ner`, from row 32a's install); `tini`, CA certificates, the user, the marker and two links are
  the only additions.

## 5. Behavior

### 5.1 Build inputs

Per release and architecture: `decoy-<ver>-linux-<arch>.tar.gz` plus `.sig` and `.sha256`
produced by REL-PKG, and the release's `install.sh` with the public key filled in. The release run
uses the same files it publishes to the download host, handed over as workflow artifacts, not
re-downloaded.

The key fill is one tool, `packaging_tools/fill_release_key.py --pub <pem> --in install.sh --out
<file>`, which replaces the `__DECOY_RELEASE_PUBLIC_KEY__` marker and refuses if the marker is
absent or appears more than once. REL-PKG's publish step and the image lane both use it; IMG-2
adds it unless REL-PKG has already landed an equal tool, in which case IMG-2 uses that one.

`packaging_tools/image_context.py` stages a Docker build context: the four files, the Dockerfile,
and the marker filled with `variant` and `version`. It refuses an `install.sh` that still carries
the placeholder (no bypass flag), so no image is ever built that trusts an unfilled key.

Inputs of the lane's dev-signed bundle (5.10), pinned in `packaging_tools/image/inputs.toml`:

- CPython: python-build-standalone at the version the certified profile names (3.10.20 today),
  through `uv python install` at a pinned uv version (uv verifies the download's checksum).
- The engine and native companion wheels: one published engine release's assets, pinned by version
  and SHA-256 per arch. This needs the engine native release workflow (packaging spec S1, row 90)
  to have published once; until then IMG-2 is blocked (section 10).
- The CLI wheel: built from the checked-out commit with `uv build`.
- The third-party closure: `pip download` constrained by `requirements-certified.txt` for the
  target platform.
- The key: a throwaway Ed25519 pair from `sign_release keygen`, made in the job, filled into
  `install.sh` with `fill_release_key.py`.

### 5.2 Image layout

Multi-stage `packaging_tools/image/Dockerfile`, both stages
`FROM debian:trixie-slim@sha256:<pinned>` (glibc 2.41, above the bundle's manylinux_2_28 floor;
trixie is Debian stable, bookworm is past regular security support):

1. Stage `install`: `apt-get install --no-install-recommends openssl ca-certificates`; run
   `DECOY_HOME=/opt/decoy DECOY_BIN_DIR=/opt/decoy/bin DECOY_LOCAL_BUNDLE=/ctx/<bundle> sh /ctx/install.sh --version <ver>`.
   The installer's own signature, checksum, manifest and native self-checks run here; any failure
   fails the build.
2. Stage `final`: `apt-get install --no-install-recommends ca-certificates tini`, apt lists
   removed; `COPY --from=install /opt/decoy /opt/decoy`, owned by root, not writable by others;
   `/usr/local/bin/decoy` is a symlink to the shim `/opt/decoy/bin/decoy` (never to the slot
   launcher, whose `dirname "$0"` would resolve to `/usr/local/bin`), and `ENV
   PATH=/opt/decoy/bin:$PATH`; `/etc/decoy/image.json` (root, mode 0444) holds
   `{"schema": "decoy-image/v1", "variant": "slim", "version": "<ver>"}`;
   `/usr/share/doc/decoy/LICENSE.md` is a symlink to the CLI wheel's `LICENSE.md` in the slot's
   `dist-info` (the build fails unless exactly one such file exists); user `decoy` with UID and GID
   10001; `HOME=/home/decoy` with mode 1777, so any UID can write it; `WORKDIR /work` (mode 1777);
   `USER 10001:10001`; `ENTRYPOINT ["/usr/bin/tini", "--"]`; `CMD ["decoy", "--help"]`.
   No `DECOY_HOME` is set in the final image: `managed_home()` derives the runtime from the
   interpreter, and settings then live at `$HOME/.decoy/settings.json`, which is writable.
   OCI labels: `org.opencontainers.image.version`, `.revision`, `.source`, `.licenses`
   (`FSL-1.1-ALv2`), `.title`.

The build strips setuid and setgid bits the base ships, and records `dpkg-query -W` output as a
build artifact (the OS package list the Python SBOM does not cover). Buildx runs with
`--provenance=false --sbom=false`; provenance comes from `attest-build-provenance` instead, so the
index holds exactly the two platform manifests.

### 5.3 Tags, digests and the per-release record

Per release `X.Y.Z`: tags `X.Y.Z`, `X.Y`, `X`, `latest` for slim, and `X.Y.Z-ner`, `X.Y-ner`,
`X-ner`, `ner` for the NER variant (5.7). Full-version tags are never moved or deleted. Moving tags
move only in the last job, after the signed record is verified. Docs and recipes always pin
`@sha256:<index digest>`; tags are for discovery.

The per-release record `images.json`, signed with `sign_release sign` (detached `.sig`, the same
Ed25519 release key) and published beside that release's bundles at `<base>/<ver>/images.json`,
stays there for every release:

```json
{
  "schema": "decoy-images/v1",
  "version": "1.0.0",
  "images": {
    "slim": {"ref": "<registry>/<name>:1.0.0", "digest": "sha256:<index digest>"},
    "ner":  {"ref": "<registry>/<name>:1.0.0-ner", "digest": "sha256:<index digest>"}
  }
}
```

The version document gains the same `images` object as an optional top-level field, for discovery
of the latest release only (additive; unknown top-level fields are ignored by contract,
`docs/distribution/version-endpoint-contract.md:71`). Any re-signing of the version document
carries the field forward unchanged.

### 5.4 Signing and verification

- The `sign` job (Environment `native-release`): `cosign sign --recursive` on each index digest
  (keyless, GitHub OIDC), build provenance via `actions/attest-build-provenance`, and
  `cosign attest --type cyclonedx` with the bundle's SBOM. Then the online check below against the
  pushed digests. No tag moves here.
- Online check (docs): `cosign verify <ref>@<digest> --certificate-oidc-issuer
  https://token.actions.githubusercontent.com --certificate-identity-regexp
  '^https://github\.com/<owner>/decoy/\.github/workflows/image\.yml@refs/tags/v[0-9]+\.[0-9]+\.[0-9]+$'
  --certificate-github-workflow-trigger push`. `<owner>` is the repository owner after OQ-2.
- Offline check (docs, the high-assurance path): verify `images.json` with the pinned release key
  exactly as the install docs verify bundles, then compare its digest with the mirrored image's
  digest. This needs no new key and no transparency-log access, and works for any older release.
- The `promote` job runs the offline check on the signed `images.json` against the pushed digests
  before it moves any tag.

### 5.5 License refusal

Working answer to OQ-1 (option a): the license is valid when `DECOY_ACCEPT_LICENSE`, stripped
and compared without case, equals `FSL-1.1-ALv2`. `ACCEPTED_LICENSE_ID` is a constant in
`image_gate.py`; a test ties it to the `## Abbreviation` line of the repo's `LICENSE.md`, so a
license change cannot leave the gate on the old id.

In image mode, the root callback refuses before any other work when the value is unset, empty or
anything else:

```text
error: [image.license_not_accepted] This Decoy container image runs only after you accept its
license. Read it at /usr/share/doc/decoy/LICENSE.md, then set DECOY_ACCEPT_LICENSE=FSL-1.1-ALv2.
  hint: see the container guide: https://decoy.dev/docs/container
```

- Exit 1 (`EXIT_USAGE`): the fix is in the user's invocation. No new exit code.
- Written through `emit_error` in human mode to stderr; stdout stays empty. The root callback runs
  before a subcommand parses `--json`, so a `--json` caller gets exit 1 and empty stdout, the same
  as today's native runtime refusal (V2-LOG: root refusals as a `decoy-error-v1` object).
- The text is fixed. It never contains the variable's value, a path from the environment, or
  anything read from the marker.
- The root group's eager options run during the group's own argument parsing, before the root
  callback, and so are not gated: `decoy --version`, `decoy --help`, `--install-completion` and
  `--show-completion` (the last two are Typer's; `--install-completion` writes the user's shell rc
  under HOME, which is the user's own file). Bare `decoy` prints help and exits 2, as today
  (`no_args_is_help`). `decoy <command> --help` is parsed after the root callback (Click runs the
  group callback, then builds the subcommand's context), so it is refused like the command itself;
  the refusal says how to accept. The default `CMD` is `decoy --help`, which works unaccepted.

Option (b), if the owner picks it in OQ-1, replaces only `image_gate._license_ok()` with an
offline Ed25519-signed license file check (`/run/secrets/decoy-license` or
`DECOY_LICENSE_FILE`), verified against a separate pinned license key with
`decoy.distribution.signing.verify_detached`, adding the code `image.license_invalid`. Everything
else in this plan stays. It also needs license issuing tooling, a second key with custody, and a
customer delivery flow, which this plan does not cover (section 13).

### 5.6 Other image-mode behavior

- `decoy upgrade` refuses with `image.upgrade_unsupported`, exit 1: "This command upgrades a
  downloaded install. In a container, pull a newer image instead." It runs no network call. The
  check sits in `image_gate.enforce`, so `upgrade.py` does not change.
- The startup update notice never runs in image mode: the root callback adds `image_mode()` to the
  existing `suppress=` condition.
- Order in the root callback: `image_gate.enforce`, then `runtime_guard.enforce`, then the update
  notice. The license refusal therefore wins over a native-companion refusal: an unaccepted image
  never reports internals.
- `decoy setup --yes` writes `$HOME/.decoy/settings.json` (no `DECOY_HOME` in the image), so it
  works for any UID (T-I3).

### 5.7 The `-ner` variant

Built `FROM` the slim image's final stage. Where spaCy and the model live for a bundle install is
row 32a's decision; the `-ner` image follows it and has no NER install path of its own:

- The build switches to `USER root` for one `RUN` line that runs row 32a's model-install command
  in its offline mode, with the spaCy closure and the model wheel pinned by hash
  (`NER_MODEL_WHEELS` for `DEFAULT_NER_MODEL`, today `en_core_web_sm` 3.8.0), then back to
  `USER 10001:10001`.
- `DECOY_ACCEPT_LICENSE` is set only on that `RUN` line (`RUN DECOY_ACCEPT_LICENSE=... decoy
  ...`), never as `ENV`, so the published `-ner` image is not pre-accepted (T-I4 runs on `-ner`).
- The command must write no `.pyc` and must leave the signed slot either untouched (its files in a
  named path outside the slot) or touched only at paths its own install record lists. IMG-5's
  T-I1 variant runs `verify_extracted` on the slot and allows exactly the paths that record names;
  if 32a cannot meet that, IMG-5 stops and reports instead of weakening T-I1.
- The marker says `"variant": "ner"`.

Until row 32a's model-install command is merged, the `-ner` tags are not published and the release
ships slim only (OQ-4).

### 5.8 Runtime posture

- Default user 10001; any other non-root UID works because HOME and `/work` are mode 1777 and
  nothing under `/opt/decoy` is written at run time (the launcher runs `-I -B`, so no bytecode is
  written).
- Read-only root filesystem works with a writable `/tmp` and HOME (tmpfs or `emptyDir`), plus the
  mounted work folder.
- TLS: `ca-certificates` is in the final image, so clients that use the system store (webhook
  notifications through `urllib`, `src/decoy/notify.py:254`) verify certificates.
- Secrets reach the container only through the environment or mounted files the user supplies
  (`DECOY_MASK_SECRET` and cloud credentials as the CLI already reads them); the image holds none.

### 5.9 Public docs and recipes

`docs/guides/container/README.md` (synced to decoy.dev by REL-DOCS, row 92) covers: pull by digest,
accept the license, verify (online and offline), mount a project, pass `DECOY_MASK_SECRET`, exit
codes, the GitLab clone-ownership note (a non-root image relies on the runner's default umask for
the cloned `/builds` tree), and the three recipes, each a complete file beside the guide:

- `github-actions.yml`: one job, a `docker run --rm --user "$(id -u):$(id -g)"
  -v "$GITHUB_WORKSPACE:/work" -e DECOY_ACCEPT_LICENSE -e DECOY_MASK_SECRET <ref>@<digest> decoy run
  <pipeline>` step, with the secret from repository secrets.
- `gitlab-ci.yml`: `image: <ref>@<digest>`, variables from masked CI/CD variables, `script:
  decoy run <pipeline>`.
- `k8s-job.yaml`: a Job meeting Pod Security "restricted": `runAsNonRoot`, `runAsUser: 10001`,
  `runAsGroup: 10001`, `fsGroup: 10001` with `fsGroupChangePolicy: OnRootMismatch`,
  `readOnlyRootFilesystem`, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`,
  `seccompProfile: RuntimeDefault`, `emptyDir` on `/tmp` and `/home/decoy`, the project from a
  PersistentVolumeClaim, the license and mask secret from a Secret. The container sets `args:`
  only, never `command:`, because `command:` replaces the image's `tini` entrypoint.

Recipes use the placeholder `<ref>@<digest>`; the release run writes the real digest into the
published docs page.

### 5.10 CI job placement

One workflow, `.github/workflows/image.yml`. It has automatic triggers, so it needs no
`ci/unlaned.toml` entry, and no path filter, so the shrink-only `[[path_filter]]` list does not
grow:

- Triggers: `push` to `main`, a weekly `schedule`, `workflow_dispatch` (with an `arch` input), and
  `workflow_call` with a boolean input `release` (REL-PKG's release workflow calls it with
  `release: true` and the bundle artifacts).
- Image slice PRs (IMG-2 to IMG-5) run it with `workflow_dispatch` on their branch and record the
  run in the PR. Other CLI PRs are not held by it; a break shows on the next `main` push or the
  weekly run, and the release run tests everything again before anything is published.
- Concurrency: `group: image-${{ github.ref }}-${{ inputs.release || 'lane' }}`,
  `cancel-in-progress: false` (a publish must never be cancelled halfway; the workflow has no
  `pull_request` trigger, so the shared PR concurrency block does not apply).
- Every job sets `timeout-minutes` (lane build 45, test 30, release jobs 30 each).

Jobs:

| Job | Runs when | Runner | Permissions | Does |
|---|---|---|---|---|

### 5.11 Release and rollback

An image is part of the release unit (bundles, images, `images.json`, version document).
Preconditions: both arches built from the signed bundles, every `tests/container/` test green on
each arch, signatures verified. If any step before `promote` fails, no tag moves and the version
document is not published; pushed digests stay untagged and inert. Rollback: point the moving tags
back to the previous index digest and publish the version document that names it; never delete a
published digest or its `images.json`, since users pin them. Post-release signal: `promote` pulls
and runs each moving tag once before the release is announced.

## 8. Choke point, enumerations and class table

### 8.1 Choke point

The rule "every `decoy` command in an image is gated" is enforced by construction in the Typer
root callback, which runs before every subcommand. Guard: T-G10's AST check plus T-G1, which walks
the registered command list from `app`, so a new command is covered without editing the test.
Mutation: removing the call turns both red.

### 8.2 Exit paths of the gate and the build

The gate sits in the root callback at `src/decoy/__main__.py:252`, before the update notice at
`src/decoy/__main__.py:260`; `--version` exits in its eager callback at
`src/decoy/__main__.py:208`.

Run time (CLI, in image mode):

1. Not accepted: exit 1, `image.license_not_accepted`, nothing read or written (T-G1, T-G2, T-I4).
2. Accepted, `upgrade`: exit 1, `image.upgrade_unsupported`, no network (T-G7).
3. Accepted, native self-check fails: today's `runtime_guard` refusal, exit 3 (unchanged).
4. Accepted, any other command: the command's own exits, unchanged (T-G3, T-I3).
5. Root eager options: exit 0 before the gate; bare `decoy`: exit 2 as today (T-G6).
6. Marker unreadable, a link or malformed: path 1 or 2 as for a good marker (T-G5).

Build and release (each stops the release with nothing published past that step): key fill
refusal; `image_context.py` refusal; `install.sh` refusal in the build stage; license link not

## 13. Owner questions (each with a recommended answer)

- **OQ-1. What counts as "a valid license" for the public image?** The CLI has no license-key
  system: FSL-1.1-ALv2 grants use for permitted purposes without a key, and the paid platform's
  key is deliberately not enforced (license-enforcement-v1). Options: (a) accept-license
  variable, `DECOY_ACCEPT_LICENSE=FSL-1.1-ALv2`, the established `ACCEPT_EULA` pattern; no key, no
  network, works air-gapped. (b) An offline Ed25519-signed license file per customer, verified
  against a pinned license key; needs issuing tooling, a second key with custody and a delivery
  flow, and matches a paid CLI tier that does not exist today. **Recommended: (a)**; (b) stays a
  V2-LOG item and swaps one function if chosen later.
- **OQ-2. Registry and image name.** Options: GHCR under a GitHub organization for the licensor
  (for example `ghcr.io/<org>/decoy`), GHCR under `louiskeep`, or Docker Hub (anonymous pull rate
  limits unless paid). The name is hard to change after launch because users pin it.
  **Recommended: GHCR under an organization** (owner creates it), public package, free for public
  images; `louiskeep` only if no organization is planned.
- **OQ-3. Signing method.** Options: cosign keyless with the GitHub OIDC identity (each signature
  is a public Rekor entry naming the repository and workflow; no key to hold; trust rests on who
  can push `v*` tags), or cosign with a long-lived key held in `native-release`.
  **Recommended: keyless** with the tag ruleset below, plus the per-release Ed25519-signed
  `images.json` as the high-assurance check that uses the existing release key.
- **OQ-4. `-ner` without row 32a.** If the model-install command is not merged by a release, ship
  slim only and add `-ner` in the first release after it lands. **Recommended: yes**, so the image
  never carries an NER install path of its own.

Owner tasks this plan needs before IMG-4 (setup, no product decision): create the organization or
choose the namespace (OQ-2); add a tag ruleset that limits creating `v*` tags to the owner; add a
deployment rule on the `native-release` Environment that allows only `v*` tags; make the package
public after the first push.

## 14. Pre-mortem

  environment deployment rule stop it, and the Ed25519 `images.json` check does not depend on it.

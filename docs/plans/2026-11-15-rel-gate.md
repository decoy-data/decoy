## 1. FRAME

### Guarantee (what REL-GATE promises)

1. **One frozen-surface map per repo.** Every surface in the CLI's `docs/release/versioning.md` "Public
   surface" list, the CLI Python API and version document, and every surface in engine compatibility contract
   sections 3.1 to 3.5 has one row in its repo's frozen-surface map with the test that pins it.
   Each row names its completeness source; a surface from a source with no row, or a row whose test does not
   exist, turns a sentry red.
2. **Snapshots for the unpinned surfaces.** The YAML pipeline schema, the run-result schema and one
   representative success document per `--json` command each have a committed snapshot that a test compares
   byte for byte. Shape snapshots hold no cell value; declared dynamic-map keys collapse to `*`. Any change
   shows up as a snapshot diff in review.
3. **The launch pin is the D-4 tag.** One check proves that `lock_version.sh --engine-spec` names the D-4 tag,
   then runs the existing pin-agreement sentry and `lock.sh --check`, and that the CLI version agrees in
   `pyproject.toml`, `decoy.__version__` and `decoy --version`.
4. **A recorded canonical smoke.** The canonical R1 smoke installs the signed release-candidate bundle on each
   supported platform with the candidate's own key-embedded installer, refuses a build that still carries the
   placeholder release key, runs `decoy --version`, `decoy doctor --json`, a native-eligible keyed mask run that must
   report `native_route.state == "native"`, and a plain run of the bundled `minimal` template. Each green run
   appends one row to `docs/release/smoke-log.md`, checked against a candidate record written at G5.
5. **A filled readiness instance.** A template lists every gate with its command, pass criterion, evidence and
   owner. The instance for 1.0.0 is a dated record carrying the release identity. A checker refuses an
   instance with a missing row, an empty result, an identity that drifted or differs from the candidate record, a
   missing `accepted-known-limit` cell, or no owner sign-off. A release
   tag without a complete instance is a draft, not a release.
6. **A wording checkpoint.** One license id (FSL-1.1-ALv2) and one install story (signed bundle; public
   `pip install` later) across the CLI and engine docs, pinned by the existing metadata tests. At readiness
   time the checker refuses every `TODO(counsel)` and `TODO(licensor)` marker and requires every copyright and
   licensor line in both repos to equal the licensor value counsel gives. It decides nothing for counsel.

### Non-goals

- Publishing anything, signing anything, creating the signing key or the `native-release` Environment
  (rows 90 and 94; owner tasks).
- Deciding the licensor entity, a contributor license agreement, or whether a CLA gates 1.0.0 (owner and
  counsel; Q1, Q2).
- Post-launch compatibility diffs against the 1.0.0 tag (`griffe check`, schema diff). They matter from the
  first monthly release, not for 1.0.0 (FU-1; Q6).
- The website download page and docs flip (rows 91, 92), the container image (row 90a), Windows
  feasibility (row 89), the QA checklists (row 92a), how pip extras reach bundle users (rows 90, 92).
  REL-GATE reads their results; it does not build them.
- Changing any frozen behaviour. The slices add checks and docs. The one behaviour change, the engine
  pre-GA to GA flip, is its own slice pair gated on Q3.

### Failure modes

- A frozen surface changes after the freeze and nobody notices (silent contract drift).
- The CLI ships pinned to an engine other than the one QA tested.
- The smoke runs green on an artifact that is not the one released (wheel instead of bundle, or a bundle
  built from another commit), or on a route that never touched the native path it claims.
- A readiness instance is "filled" with blank or copied rows, or names an identity that moved after QA.
- The release ships with a placeholder licensor or contradicting install instructions.
- A snapshot regenerates silently in a dependency bump (for example a pydantic upgrade reshapes
  `model_json_schema()`) and the reviewer accepts it as noise.

## 2. Established solutions

Searched first (2026-11-15), then read against the repos:

- **Public Python API breakage:** Griffe's `griffe check <pkg> --against <tag>` compares a package's API
  with a git ref and exits 1 on a breaking change; NVIDIA Megatron Core runs it in CI. Fits the engine's
  46-parameter `run_pipeline` and root exports after 1.0.0 (FU-1). Nothing to compare against for the first
  release, so it is not in the 1.0.0 gate.
- **Schema compatibility:** Buf's breaking-change detection and Confluent Schema Registry compatibility
  modes are the established pattern for wire schemas (backward, forward, full). For JSON Schema the tools
  are young (`jsoncompat` for Draft 2020-12, `json-schema-diff`, `api-schema-diff`). For 1.0.0 we take the
  simplest established form: a committed generated schema with a byte-equality test, the pattern the CLI
  already uses for `docs/schemas/decoy-ci-v1.schema.json`
  (`tests/unit/test_ci_manifest.py::test_generated_schema_matches_the_committed_schema_byte_for_byte`).
- **CLI stability contracts:** projects reaching 1.0 pin the exit-code table, the command and flag set and
  the machine-readable output in tests, and check them against the docs (for example a Codeberg PR "test:
  pin the 1.0 stability contracts"). Golden tests run on `--json`, never on human text. The CLI already
  pins the command and flag set (`tests/unit/test_cli_surface.py` re-renders `docs/cli-reference.md`) and the
  exit codes; this plan adds the `--json` shapes.
- **Release readiness:** a production-readiness checklist with named commands, evidence per row and a
  sign-off (Google SRE PRR; the platform's archived `v1-release-readiness.md`: "A release tag without all
  commands green + all manual gates marked is not a release; it is a draft"). We reuse its structure.
- **Release smoke from the shipped artifact:** install the exact signed artifact on a clean host and run a
  real command (packaging spec build step 5; `packaging_tools/smoke_install.py` already does this over a
  loopback-only HTTP server with a throwaway key).

## 3. Design notes

1. **The map is the choke point for "what is frozen".** Each repo has a frozen-surface map (CLI
   `docs/release/frozen-surfaces.md`, engine `docs/frozen-surfaces.md`): a
   table of surface, completeness source, owning code, pinning test or corpus. The sentry
   (`tests/sentry/release/test_frozen_surface_map.py` in each repo) parses it with the same pattern as
   `tests/sentry/layout/test_codemap_paths.py`, checks that every named path exists, and enumerates each
   completeness source from code or from the source document, refusing an item with no row:
   - CLI: the five items of `docs/release/versioning.md` "Public surface" (commands and flags, exit-code
     integers from `exit_codes.__all__`, the YAML schema, every leaf command with `--json`, the bundled
     template names); the lazy exports of `src/decoy/__init__.py` (`mask`, `scan`); every file in
     `docs/schemas/`; the version document and installer contract in `src/decoy/distribution/`; the
     `cli-local-1` evidence payload.
   - Engine: every format tag in the compatibility contract 3.1 tag block; every name in `decoy_engine.__all__`
     and the `sdk` exports (3.4; `PUBLIC_BOUNDARY_FILES` is an import-boundary list, not the frozen symbol set);
     the disguise registry (3.5); the vault (3.2); the determinism guarantee
     (3.3).
   Rows may point at an existing corpus (`tests/integration/compat_corpus/records/`, `run_result/`) where one
   already pins the format. A surface that has no pinning test yet is a row whose test cell says
   `accepted-known-limit: <V2-LOG id>`; the readiness instance then shows it, and `readiness_check.py
   --engine-repo` refuses an instance that leaves one out (design note 5).
   Mutation: delete a row for any source item, or point a row at a missing test.
2. **Shape snapshots are value-free for cells.** A `--json` shape records key paths and JSON types (`object`,
   `array`, `string`, `integer`, `number`, `boolean`, `null`), never a cell value. Object keys can carry data
   (maps keyed by table, column or category), so each command's entry declares its dynamic-map pointers, and
   their keys collapse to `*`. Inputs are synthetic files built per test from
   `tests/fixtures/qa_first_user/` (copied to `tmp_path`); the test plants a marker string as a column name and
   as a cell value and asserts it never reaches the snapshot. One run per command captures one representative
   success document; keys that appear only on some paths (in `decoy run --json`: `subset`, `notify`,
   `native_route`, `report`, `src/decoy/cli/run/_render.py:105-130`) are listed per command as optional keys,
   and the map row says the snapshot covers the listed paths only.
3. **Schemas are generated, then committed.** The engine writes `PipelineConfig.model_json_schema(mode=
   "validation")` and `RunResult.model_json_schema(mode="serialization")` (the modes differ:
   `tests/unit/config/test_pipeline_config_validation.py:591-604`) as documents with
   `json.dumps(sort_keys=True, indent=2, ensure_ascii=False)` plus a newline. The `_canonical` foundation
   (`canonical_json_bytes`, `_canonical/_json.py:136`) writes compact digest bytes and is not used for a
   document meant to be read. Limit: validator logic and runtime defaults (DE-03 through `is_pre_ga`) do not
   appear in a schema, so the snapshot pins the field set and types, not behaviour; behaviour stays with the
   existing unit tests. The pydantic pin in the certified lock keeps generation stable (pre-mortem P3).
4. **The launch pin check adds one question and reuses the rest.** Agreement across sites is already proven by
   `tests/sentry/test_ci_lock_installs.py::test_lock_profile_lives_in_lock_version_and_the_policy` (workflow
   literals equal `lock_version.sh --engine-spec`, registered in `ci/install-policy.toml:30-45`, and the tag
   equals the pyproject pin) and `scripts/dev/lock.sh --check` (re-resolves `requirements-dev.lock`). The new
   check asks only whether `--engine-spec` ends in `@<D-4 tag>`, then runs those two as reported steps. It
   keeps no list of its own, so a sixth site is caught by the existing scanner.
5. **The readiness checker validates structure and identity, not truth.** It checks that the instance has every
   template row; each result is one of `pass`, `fail`, `accepted-known-limit`; each `pass` row cites an evidence
   link (run URL, record path or SHA); `accepted-known-limit` rows name the V2-LOG id; `cli_sha`, `engine_tag` and
   `engine_commit` recorded at G3 equal their G7 values, and `sha256sums_sha256` recorded at G5 equals its G7 value
   (or a rerun row exists for the later identity); under `--candidate`, the G7 identity equals `candidate.json`
   field for field; under `--engine-repo`, every `accepted-known-limit` cell in the CLI and engine frozen-surface maps
   appears as an instance row with the same V2-LOG id; and the sign-off block names the owner and a date. Whether a
   row's criterion was met is not something a parser can see: truth comes from the commands each row names.
6. **The smoke records itself against an independent record.** At G5 the build calls the new
   `packaging_tools/candidate.py`, which writes `SHA256SUMS` (sorted `sha256  name` lines over every tarball,
   `.sig`, installer and the version document; today `build_bundle.py` writes only one `.sha256` per tarball) and a
   candidate record (`candidate.json`: CLI version, CLI SHA, engine tag and commit, the SHA-256 of `SHA256SUMS`)
   next to the signed set, and the readiness instance stores the same digest. `scripts/release/record_smoke.py
   SUMMARY.json --candidate candidate.json --run URL_OR_HOST` appends a row only when the summary matches the
   candidate record. It refuses a red run, an unknown summary schema major and non-strict field types, and
   never rewrites an existing row.

Rollback: REL-GATE publishes nothing, so a failed gate leaves no public artifact to roll back. Candidate

recorded reason and a changelog line. Post-release signals, observation and the version-document rollback
belong to row 94 (packaging spec, "Release and rollback").

### 5.8 Exit-code agreement (slice RG-X, CLI, merged before G2)

Facts at CLI main `5628920`:

Decisions (made here, inside the freeze scope; none is an owner call):
- **Crash exit stays 1.** Shipped code exits 1 and a sentry pins it four times; 3 appears only in prose. The docs move

  aborted prompt; stderr tells them apart (`error: internal error (<Type>)` for the crash). The 3 for an engine error
  a command catches stays as documented.
- **One precedence, the `decoy ci` order `5 > 3 > 1 > 6 > 4 > 2 > 0`.** It is a published contract
  (`docs/ci-contracts.md`), pinned by two unit tests, and already places 6. The `run --all` order has no 6, and no
  release carries it. Capacity before runtime also matches what a caller should do first: a capacity refusal is fixed
  by the host, not by a rerun.

## 14. Pre-mortem

- **P1 The freeze happens on a moving main.** A V1 fix merges after G3 and nobody reruns the snapshots. Guard: the
  identity block (G3, G5 and G7, 6.4), AT-R4 and AT-R5; the version bump lands in G2, so G5 builds the G3 SHA.
- **P2 Snapshot fatigue.** Reviewers wave through regenerated snapshots. Guard: the engine preflight prefix forces
  the section-9 checklist; a CLI PR that changes `json-shapes.json` without a `CHANGELOG.md` diff fails the
  `ci.yml` shape-changelog step (5.2, AT-F2f), so the rule is a check, not a reviewer's memory.
- **P3 Pydantic or Typer upgrade reshapes generated output.** The schema or reference text moves with no contract
  change. Guard: the certified lock pins both; a bump is reviewed as a contract change and the diff read, never
  regenerated blind.
- **P4 The shape test is flaky or overclaims.** Commands that print timings or paths change types between runs, and
  one document misses optional keys. Guard: shapes record the union of observed types; optional keys are listed as
  not covered; a machine-dependent command gets a stated exemption.
- **P5 The key or the signing workflow is missing.** The owner key and `native-release` Environment do not exist
  yet (row 90 owner tasks), the shipped public key is a placeholder, and no CLI build-and-sign workflow exists.
  Guard: the public key is a G2 precondition, so a missing key surfaces before the freeze; the workflow is row 94's
  precondition slice CLI-REL S0, due before G5 (FU-6); RG-S builds and tests against a throwaway key with a key-embedded test installer; readiness
  rows 8 and 9 stay red until both land. Without the key commit, 1.0.0 would install fine and then refuse every
  `decoy upgrade` (`NoPinnedKeyError`, `src/decoy/distribution/release_key.py:47-61`).
- **P6 Counsel answers late.** Guard: day-to-day wording checks are green now; only the release-time licensor check
  stays red, and the instance shows that one row and its owner.
- **P7 The Mac is busy or moved.** macOS arm64 smoke has no other host. Guard: the smoke takes minutes; check the
  Mac's lock first; if the address changed, ask Cam (mac-mini-node skill).
- **P8 A contract-named guard is dead at freeze.** The 3.3 determinism golden has no reader. Guard: RG-F1 wires one
  or corrects the contract text and records an `accepted-known-limit` row; nothing is deleted.
- **P9 Engine patch releases after D-4 skip a check.** Guard: every patch goes through `cut-release.sh`, and G2
  onward rerun with a new identity recorded.
- **P10 A native smoke that cannot pass gets weakened.** Guard: the smoke owns its native-eligible pipeline; AT-S2
  pins `state == "native"`, and M-S2 shows that accepting `applicable` goes red.
